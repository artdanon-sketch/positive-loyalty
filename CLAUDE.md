## Железные правила

Эти пять нарушать нельзя ни при каких обстоятельствах. Если задача требует нарушить — остановись и скажи.

### 1. Баллы меняются только через ledger

Никогда не пиши `prisma.membership.update({ data: { pointsBalance: ... } })` вне `LedgerService`. Баланс — производная от журнала, а не самостоятельное поле.

```ts
// ❌ никогда
await prisma.membership.update({ where: { id }, data: { pointsBalance: 1000 } })

// ✅ только так
await ledger.earn({ membershipId, amount, idempotencyKey, source, actorType, actorId })
```

### 2. tenantId только из токена

```ts
// ❌ никогда
const tenantId = req.body.tenantId

// ✅ только так
const tenantId = this.tenantContext.get()   // AsyncLocalStorage, заполнен из JWT
```

### 3. Идемпотентность на всех финансовых мутациях

Нет `Idempotency-Key` — `400`. Повтор с тем же ключом возвращает первый ответ, а не создаёт вторую операцию.

### 4. Деньги — целые числа в минорных единицах

690 ฿ = `69000`. Никаких `float`, никакого `number` для расчётов с округлением на клиенте. Форматирование только на выводе.

### 5. PII не попадает в логи

Телефоны, коды, токены маскируются на уровне логгера. Не «мы стараемся» — маскирование в транспорте логгера.

### 6. Партнёрства — надстройка над Offer, а не параллельная система

PartnershipTerm при активации порождает Offer с visibility PARTNER. Выдача и погашение идут через существующие OfferGrantService и POS API. Никаких отдельных «партнёрских кодов» и отдельных таблиц погашения. Денежных расчётов между тенантами нет никогда.

## Как добавлять эндпоинт

Порядок фиксированный, не меняй его:

1. Схема запроса и ответа в `packages/contracts/src/<домен>.ts` через zod
2. Контроллер в NestJS, валидация через `nestjs-zod`, DTO выведены из схемы
3. Сервис с бизнес-логикой — контроллер только маршрутизирует
4. Тест: happy path + минимум один негативный + кросс-тенантный
5. Пример запроса и ответа в `docs/02_API_контракты.md`
6. `@ApiResponse` для всех кодов ошибок

```ts
// packages/contracts/src/pos.ts
export const CommitTransactionInput = z.object({
  previewId: z.string().uuid(),
  receiptId: z.string().min(1).max(64),
  paidBy: z.enum(['CASH', 'CARD', 'PROMPTPAY', 'OTHER']).optional(),
}).strict()

export type CommitTransactionInput = z.infer<typeof CommitTransactionInput>
```

`.strict()` обязателен: без него лишние поля проходят и открывают mass assignment.

## Как менять схему базы

1. Правка `prisma/schema.prisma`
2. `pnpm prisma migrate dev --name осмысленное_имя`
3. Миграция **обратимо совместима**: сначала добавляем колонку nullable, деплоим, заполняем, только потом делаем NOT NULL отдельной миграцией
4. Обновить `prisma/seed.ts`, чтобы локальная база оставалась рабочей
5. Если таблица тенантная — добавить RLS-политику в той же миграции

**Никогда не удаляй колонку в одном релизе с кодом, который перестал её использовать.** Между ними должен быть хотя бы один деплой.

## Definition of Done

Задача считается сделанной, когда:

- [ ] Код компилируется в strict, `any` отсутствует (или помечен `// eslint-disable` с причиной)
- [ ] Тесты написаны и зелёные, включая негативный сценарий
- [ ] Кросс-тенантный тест зелёный, если задача трогает данные
- [ ] Схема в `contracts` обновлена, типы выведены из неё
- [ ] Пример запроса и ответа добавлен в ТЗ
- [ ] Пустое состояние, состояние загрузки и ошибки реализованы (для UI)
- [ ] Работает в обеих темах (для UI)
- [ ] Локализация: строки в JSON, не в коде (для UI)
- [ ] Секретов в диффе нет
- [ ] `pnpm lint && pnpm typecheck && pnpm test && pnpm format:check` проходит локально

`format:check` — это отдельный шаг в CI, и он валит сборку так же, как упавший тест. Если пропустить его локально, узнаешь о красной сборке уже в PR. `pnpm format` чинит форматирование на месте.

## Что делать нельзя

- Тянуть UI-библиотеку целиком (MUI, Ant, Chakra). Radix-примитивы + свои стили — можно.
- Хардкодить цвета. Только токены из `packages/ui/tokens.css`.
- Писать бизнес-логику в контроллере или в React-компоненте.
- Обращаться к Prisma из фронта или из контроллера напрямую.
- Отключать типизацию через `as any`, чтобы «быстро проверить».
- Добавлять зависимость без обсуждения, если она весит больше 50 КБ в бандле.
- Коммитить в `main` напрямую.
- Оставлять `console.log` в коде — есть логгер.

## Что делать, когда не уверен

Не угадывай в этих случаях — спроси:

- Задача противоречит ТЗ
- Требуется изменить схему ledger или логику идемпотентности
- Нужно добавить поле с персональными данными
- Нужно ослабить проверку безопасности «чтобы заработало»
- Появляется третий способ делать то, что уже делается двумя

В остальном действуй сам: мелкие решения по имплементации не требуют согласования.

## Демо-данные

`prisma/seed.ts` создаёт полигон, на котором можно работать без реальных данных:

- 3 тенанта: ресторан Kata Beach Kitchen, спа Sabai Thai Massage, прокат Phuket Ride
- по 4 сотрудника с разными ролями
- 200 гостей: 60% туристы, 40% резиденты, 5% в контрольной группе
- 90 дней истории операций с реалистичной сезонностью и провалом 14–17
- по 4 акции на тенанта в разных статусах
- один тенант с намеренно подозрительной активностью кассира — чтобы антифрод было на чём проверять

Seed должен быть детерминированным: фиксированный seed генератора, чтобы скриншоты и тесты не плыли.
