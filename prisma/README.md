# prisma — схема, миграции, генерация клиента

Здесь живёт всё, что касается PostgreSQL. Схема одна на монорепо: единый источник
правды и одна история миграций.

| Файл | Что это |
|---|---|
| `schema.prisma` | Модели. Задача 2 — `Tenant`, `Guest`, `Membership`, `LedgerEntry` |
| `migrations/` | История миграций. Только вперёд, файлы задним числом не правятся |
| `../prisma.config.ts` | Строка подключения, путь к схеме, команда seed (Prisma 7 больше не берёт их из `schema.prisma`) |
| `seed.ts` | Демо-полигон: тенанты, гости, участия и короткая история покупок |
| `test-sales.ts` | Демонстрация: пять продаж, повтор ключа идемпотентности, отмена |
| `demo-data.ts` | Сам набор демо-данных. Детерминированный: фиксированное зерно, id из индекса |
| `api-runtime.ts` | Загрузка `LedgerService` и `PrismaService` из собранного `apps/api/dist` |
| `console-table.ts` | Форматирование сумм и таблиц для вывода скриптов |
| `tsconfig.json` | Проект для скриптов этой папки: они не входят ни в один пакет монорепо |

Клиент генерируется в `apps/api/src/generated/prisma` и в репозитории **не хранится**:
его собирает `postinstall` после каждого `pnpm install`. Импорт из кода —
`./generated/prisma/client` относительно `apps/api/src`.

## Команды

Все запускаются из корня репозитория.

```bash
pnpm db:generate   # пересобрать клиент Prisma (в базу не ходит)
pnpm db:migrate    # создать и накатить миграцию на локальную базу — разработка
pnpm db:deploy     # накатить уже готовые миграции — CI и продакшен
pnpm db:seed       # демо-данные
pnpm demo:sales    # пять тестовых продаж на демо-госте: показать, что всё работает
pnpm db:studio     # веб-просмотрщик базы
pnpm db:reset      # снести базу, накатить всё заново, прогнать seed — ТОЛЬКО локально
```

### Почему seed требует собранного API

`seed.ts` и `test-sales.ts` меняют баллы только через `LedgerService` — это железное
правило 1 из `CLAUDE.md`, и второй реализации транзакции с ретраем в репозитории быть
не должно. Но запускает эти скрипты обычный `node --experimental-strip-types`, который
вырезает типы и не умеет разворачивать ни декораторы Nest, ни parameter properties —
а в `ledger.service.ts` есть и то, и другое. Поэтому скрипты берут уже собранный
`apps/api/dist`, а типы — из исходников через `import type`.

Отсюда две вещи, о которых стоит знать:

- `pnpm db:seed` и `pnpm demo:sales` сами вызывают `pnpm build:api` — руками ничего
  собирать не нужно;
- `pnpm db:reset` зовёт seed напрямую через Prisma CLI и сборку не делает. Если
  `apps/api/dist` пуст, seed честно скажет об этом и назовёт команду сборки.

`DATABASE_URL` берётся из корневого `.env` (`prisma.config.ts` читает файл через
`process.loadEnvFile`). Формат и пример — в `.env.example`. Значения по умолчанию нет:
без переменной команды, которым нужна база, честно падают.

## Как накатить с нуля

```bash
cp .env.example .env          # и подставить свою строку подключения
pnpm install                  # postinstall соберёт клиент
pnpm db:deploy                # накатит prisma/migrations по порядку
pnpm db:seed                  # опционально: демо-данные
```

`db:deploy`, а не `db:migrate` — deploy только применяет готовые файлы и никогда
не переписывает историю. `migrate dev` нужен, когда вы меняете схему.

## Как откатить

Down-миграций у Prisma нет — и это сознательный выбор, а не недоработка: откат
схемы на живых данных почти всегда теряет данные молча.

- **Локально:** `pnpm db:reset`. Дропает базу и накатывает всё заново.
- **На проде:** откат делается **новой миграцией вперёд**, которая возвращает схему
  к прежнему виду. Пишется руками, ревьюится отдельно.
- **Аварийно:** восстановление из бэкапа (Supabase PITR), затем `db:deploy` до нужной
  миграции. Строки `LedgerEntry` при этом не редактируются — журнал восстанавливается
  целиком на момент снимка.

Отсюда правило из `CLAUDE.md`: миграция должна быть обратимо совместимой. Новая
колонка сначала nullable → деплой → заполнение → отдельная миграция с `NOT NULL`.
Колонка не удаляется в том же релизе, где код перестал её читать.

## Почему `LedgerEntry` append-only

Баллы — это деньги мерчанта. Строка журнала, которую можно отредактировать, перестаёт
быть доказательством: сверка сойдётся с чем угодно, если подгонять слагаемые.
Поэтому единственная разрешённая операция над таблицей — `INSERT`.

- Начисление и списание — новые строки.
- **Отмена — тоже новая строка**, `type = REVERSAL`, `reversalOfId` указывает на исходную.
  `reversalOfId` под `UNIQUE`: одну операцию нельзя отменить дважды.
- `Membership.pointsBalance` — денормализованный кэш. Источник истины — `SUM(amount)`.
  Кэш пишется только внутри той же `Serializable`-транзакции, что и строка журнала,
  и только из `LedgerService`.

Запрет прибит в миграции `20260825120000_init_ledger_core` **двумя независимыми
механизмами**, потому что каждый по отдельности обходится:

1. **`REVOKE UPDATE, DELETE, TRUNCATE`** у ролей приложения. Не действует на владельца
   таблицы: у него привилегии подразумеваются, и он может выдать их себе обратно.
   А миграции и seed ходят в базу как раз владельцем.
2. **Триггеры `BEFORE UPDATE OR DELETE` и `BEFORE TRUNCATE`**, безусловно бросающие
   исключение. Срабатывают на кого угодно, включая владельца, — но владелец может их
   выключить (`ALTER TABLE ... DISABLE TRIGGER`).

Вместе они закрывают дыры друг друга: чтобы стереть строку журнала, нужно осознанно
выполнить отдельный DDL под привилегированной ролью. Случайного `DELETE` из кода,
миграции или psql-сессии не случится.

Триггеры объявлены `ENABLE ALWAYS`: обычные молча не срабатывают при
`session_replication_role = 'replica'`, а эту настройку ставят инструменты
репликации и массовой загрузки.

`TRUNCATE` закрыт отдельно — он не `UPDATE` и не `DELETE`, построчные триггеры на нём
не вызываются, и без своего правила он вынес бы весь журнал одной командой.

### Что это значит для тестов

`DELETE FROM "LedgerEntry"` и `TRUNCATE` в teardown работать не будут — и это не
недосмотр, а то же самое правило. Чистить состояние между прогонами так:

- `pnpm db:reset` перед прогоном интеграционных тестов;
- либо создавать в каждом тесте свой `Tenant`/`Guest`/`Membership` — тогда чистить
  нечего, тесты не пересекаются;
- либо оборачивать тест в транзакцию с откатом.

## Чего здесь пока нет

- **RLS.** Политики Row Level Security на тенантных таблицах — Задача 3
  (`docs/01_Архитектура_и_данные.md`, раздел 5). Появятся отдельной миграцией
  вместе с `TenantGuard` и `AsyncLocalStorage`. Запрет `UPDATE`/`DELETE` на журнале —
  это про целостность денег, RLS — про изоляцию тенантов; задачи разные, миграции
  тоже разные.
- **Полный демо-полигон.** `seed.ts` уже есть, но покрывает только четыре
  существующие модели: 3 тенанта, 40 гостей, участия и контрольную группу.
  Сотрудники, точки, акции, 90 дней истории с сезонностью и подозрительный кассир
  из `CLAUDE.md` ждут своих моделей — список отложенного с причинами приведён
  в шапке `seed.ts`.
- **Остальные модели.** `Location`, `GuestChannel`, `Staff`, `Offer`, `Consent`,
  `Device`, `WebhookEvent`, `AuditLog`, `Broadcast`, `Certificate`, `Review` —
  в следующих задачах, по мере надобности.

## Роль приложения и RLS

Начиная с миграции `20260826120000_tenant_isolation_rls` приложение **не должно**
ходить в базу владельцем.

Причина простая и она уже подводила нас дважды: **владелец таблицы игнорирует и
`REVOKE`, и политики RLS**. Пока `DATABASE_URL` указывает на `postgres`, включённый
RLS не защищает ни от чего и создаёт ложную уверенность.

Миграция создаёт роль `positive_app` без пароля и без права входа — пароль выдаётся
в каждой среде отдельно и в репозиторий не попадает.

Локально:

```sql
ALTER ROLE positive_app LOGIN PASSWORD '<пароль>';
```

Затем в `.env`:

```
DATABASE_URL=postgresql://positive_app:<пароль>@localhost:5432/positive_loyalty?schema=public
DATABASE_URL_TEST_APP_ROLE=postgresql://positive_app:<пароль>@localhost:5432/positive_loyalty_test?schema=public
```

Миграции и `seed` продолжают выполняться **владельцем**: под RLS роль приложения
не может ни создать заведение, ни наполнить полигон, и это правильно — создание
тенанта операция платформы, а не заведения.

### Как убедиться, что RLS действительно работает

```sql
-- под ролью приложения, без объявленного тенанта
SELECT count(*) FROM "Membership";   -- обязано быть 0
```

Если вернулось не ноль — вы подключены владельцем, и изоляции нет.
