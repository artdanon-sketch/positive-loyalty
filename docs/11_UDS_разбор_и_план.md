## 1. Что у UDS действительно хорошо

Это не список экранов, а приёмы, которые делают кабинет «продуманным».

1. **Каждый экран устроен одинаково.** Заголовок, одна главная кнопка
   («Создать», «Провести операцию», «Пригласить»), под ним фильтр и поиск,
   дальше таблица или карточки. Пустое состояние объясняет, что делать,
   и даёт ссылку («нет операций за день — посмотрите за всё время»).
2. **Левое меню с иконками** и подсветкой текущего раздела; на узком экране —
   выдвижное.
3. **Настройки — витрина модулей.** Карточка на модуль: название, одна фраза
   «зачем», состояние «подключён». Отключённые модули — отдельным блоком.
4. **Карточка клиента.** Шапка: имя, статус, последняя покупка и последний
   вход. Действия: баллы, сертификат, статус. Вкладки: информация, операции,
   баллы, рекомендации, сертификаты. Плитки цифр: оборот, средний чек,
   покупки, скидка, остаток баллов, возвраты. Заметки и теги.
5. **Статистика вкладками.** Клиенты, операции, клиенты по уровням, работа
   сотрудников, RFM-сегменты. У каждой вкладки плитки с процентами и график.
6. **RFM-сегменты** — десять понятных групп («чемпионы», «в зоне риска»,
   «спящие», «новички»…) с числом покупателей, покупок, средним чеком,
   оборотом и динамикой долей от пересчёта к пересчёту.
7. **Статусы клиентов** — лестница с процентом начисления и процентом оплаты
   баллами, переход по сумме покупок или числу рекомендаций, **скрытый статус**
   для ручного назначения.
8. **Приветственные баллы** — после вступления или после первой покупки.
9. **Реферальная программа** — баллы за друга после его первой операции,
   лимит на число наград; дополнительно процент с покупок приглашённых.
10. **Обратная связь.** Оценка визита 1–5, быстрые отзывы по темам (качество,
    цены, ассортимент, сервис, персонал), кассир у каждого отзыва,
    распределение оценок, ответ владельца, **автоответ по числу звёзд**,
    отдельная вкладка жалоб и предложений.
11. **Источники трафика.** Именованные источники со своим промокодом (табличка
    на столе, Instagram, доставка) и цифрами: сколько клиентов пришло, сколько
    купило, какая выручка.
12. **Сертификаты.** Ко дню рождения — автоматически, с условиями действия;
    выдаваемые вручную; счётчики «выдано / использовано».
13. **Сотрудники.** Кассиры и менеджеры отдельными вкладками; у кассира —
    средняя оценка гостей, число приведённых клиентов, баланс мотивации.
14. **Безопасность.** История действий и подозрительная активность («клиент
    делает слишком много покупок»), условия для кассиров: номер чека,
    потолок суммы.
15. **Автоматизация сценариев:** ответ на оценку, толчок к первой покупке
    после вступления, напоминание давно не приходившим, поощрение за сумму.
16. **Обзор «Сегодня»** — финансы, покупатели (всего, новые), операции,
    и рядом карточки-подсказки «настройте то-то за пять минут».

## 2. Сверка: что у UDS → что у нас → решение

| Модуль UDS | У нас сейчас | Решение |
|---|---|---|
| Левое меню, единый вид экранов | меню в шапке, экраны разного вида | **берём** — задача У1 |
| Дашборд «сегодня» | «Обзор»: три плитки, график, советы | **оставляем**, добавляем «сегодня» и карточки запуска — У11 |
| Статистика (вкладки) | «Обзор» + «Операции» | **берём** — раздел «Отчёты», У8 |
| RFM-сегменты | нет | **берём** — У8 |
| Операции + «провести операцию» | «Операции» и «Касса» | **оставляем** |
| Клиенты: список, фильтр, экспорт | поиск и карточка гостя | **берём** фильтры, колонки, экспорт — У4 |
| Карточка клиента: действия, вкладки, заметки, теги | карточка с лентой и «Подарить» | **берём** статус, баллы вручную, заметки, теги — У4, У5 |
| Статусы клиентов, скрытый статус | схема есть, механики нет | **берём** — У3 |
| Приветственные баллы | схема есть, механики нет | **берём** — У3 |
| Баллы ко дню рождения / сертификат ко ДР | нет | **берём** — У9 |
| Реферальная программа, уровень 1 | колонка `referredById`, механики нет | **берём** — У6 |
| Реферальная программа, уровни 2–3 | нет | **не сейчас**: многоуровневые проценты похожи на пирамиду и путают гостя |
| Источники трафика с промокодами | поле `source` без справочника | **берём** — У7 |
| Обратная связь, автоответы | нет | **берём** — У10 |
| Сертификаты вручную | «Подарить» из карточки гостя | **берём** шаблоны и счётчики поверх «Подарить» — У9 |
| Акции (у UDS — в рассылках и продвижении) | движок правил и список акций | **оставляем** наше, дописываем конструктор — У2 |
| Сотрудники: оценка, клиенты | «Команда» | **берём** цифры по кассиру — У8 |
| Безопасность: история, подозрительные | аудит пишется, экрана нет | **берём** — У12 |
| Новости в приложении гостя | нет | **берём** — У13 |
| Рассылки, push | нет каналов | **позже** — нужны каналы (Б5) |
| Telegram / MAX / VK-боты, веб-виджет | вход через Telegram есть, ботов нет | **позже** — нужен токен бота от владельца |
| Товары, заказы, интернет-магазин | нет | **не берём**: это задача кассы POSitive POS, второй каталог разошёлся бы с меню кассы |
| Продвижение за деньги, UDS AI | нет | **не берём** в этот заход |
| Сгорание баллов | схема есть, механики нет | **позже** — нужен фоновый воркер (Э3) |

### Расхождение с `03` — решено владельцем

`03`, раздел 1: «у UDS 17 пунктов меню — перебор, у нас 8». Владелец просит
функции UDS. Решение: **функции берём, меню не раздуваем** — модули UDS
раскладываются вкладками внутри наших разделов.

| Раздел | Путь | Что внутри (вкладки) |
|---|---|---|
| Сегодня | `/` | цифры дня, советы, карточки запуска |
| Отчёты | `/reports` | клиенты · операции · RFM · сотрудники · источники |
| Гости | `/guests` | список с фильтрами, карточка, теги |
| Акции | `/offers` | акции · конструктор · сертификаты |
| Партнёры | `/partners` | как сейчас |
| Общение | `/feedback` | отзывы · автоответы · новости |
| Команда | `/team` | сотрудники и их цифры |
| Касса | `/pos` | как сейчас |
| Настройки | `/settings` | витрина модулей: программа и статусы, рефералы, источники, виды продаж, безопасность, система |

Девять пунктов вместо восьми: «Отчёты» у владельца спрашивают чаще всего,
прятать их в «Сегодня» — значит снова делать экран на всё сразу.

## 3. Очередь работ

Порядок — по пользе для владельца и готовности механики под экраном.
Каждая задача — отдельный PR: контракт → API → экран → тесты (интеграционный
в CI, юнит и экран локально) → мутационная проверка → ТЗ → бэклог.
Миграции — на прод после зелёного CI и до слияния. Экран без работающей
механики под ним не выкладывается.

### У1. Оболочка «как у UDS» — левое меню и единый вид экранов — СДЕЛАНО

> Сделано: левое меню с иконками и группами, подсветка текущего раздела,
> выдвижное меню на узком экране (закрывается после перехода и по Esc),
> у кассира — одна строка с кассой. Общие `PageHeader`, `EmptyState`,
> `KpiTile` приезжают вместе с экранами У3–У8, которым они нужны.

- **Экран:** левое меню с иконками (SVG в коде, без библиотек), текущий раздел
  подсвечен, группы разделены; внизу — пользователь, тема, выход. На узком
  экране меню выдвигается по кнопке. Шапка экрана: заголовок, подпись, одна
  главная кнопка справа. Общие заготовки: `PageHeader`, `EmptyState`, `KpiTile`.
- **API, данные:** нет.
- **Права:** набор пунктов по роли — как сейчас; кассиру только касса.
- **Тесты:** каждый раздел открывается из меню; кассир видит только кассу;
  мобильное меню открывается и закрывается; активный пункт отмечен
  `aria-current`.
- **Приёмка:** все существующие экраны на месте и доступны за один клик.

### У2. Конструктор акций (Б6) — СДЕЛАНО

> Сделано: сервер (создать, запустить, пауза, завершить, прогноз; статус по датам
> вычисляется) и экран `/offers/new` — шаблон, условия с живым превью и прогнозом,
> проверка и запуск или черновик; пауза и завершение с карточки. Отступления от
> docs/03 записаны там же, в разделе 4.

- **API** (только владелец):

  | Метод | Путь | Тело / ответ |
  |---|---|---|
  | POST | `/v1/admin/offers` | `CreateOfferInput` → `201 { id, status }` |
  | POST | `/v1/admin/offers/{id}/publish` | → `{ id, status }` (черновик или пауза → идёт) |
  | POST | `/v1/admin/offers/{id}/pause` | → `{ id, status }` |
  | POST | `/v1/admin/offers/{id}/end` | → `{ id, status }` |
  | POST | `/v1/admin/offers/simulate` | `SimulateOfferInput` → `OfferSimulation` |

  Партнёрские акции через эти ручки не меняются — `409 PARTNER_OFFER`; подарки
  из карточки гостя — `404`. Менеджеру — `403`.
- **Экран:** «Создать акцию» — три шага: шаблон («Вернуть гостя завтра»,
  «Кэшбэк на время», «Своя») → условия с живым превью карточки гостя
  и прогнозом на своей истории → проверка и запуск (сразу или черновиком).
  На карточке акции — «Пауза», «Запустить», «Завершить».
- **Готово заранее:** контракты, прогноз на истории, тексты акции — с юнит-тестами.
- **Приёмка:** владелец собирает «Вернём 200 ฿ за чек от 800 ฿», кассир
  на следующем чеке видит акцию в предрасчёте, гость получает код.

### У3. Статусы гостей и приветственные баллы — СДЕЛАНО

> Сделано на сервере: лестница статусов и приветственные баллы — отдельным входом
> `/v1/admin/settings/program/tiers`; ставки статуса на кассе и в вебхуке; пересчёт
> после чека (автоматически только вверх); ручной статус
> `PUT /v1/admin/guests/{guestId}/tier`; приветственные баллы — подарком в журнале,
> без визита. В бэк-офисе — блок «Статусы гостей» в настройках, чип и «Изменить
> статус» в карточке гостя, статус на кассе. В приложении гостя — статус в заведении
> и сколько осталось до следующего.

- **Механика:**
  - статус считается после каждого проведённого чека по условиям
    (сумма покупок, число визитов, число рекомендаций); ручной статус
    не пересчитывается;
  - ставки статуса заменяют базовые в предрасчёте кассы (начисление
    и доля оплаты баллами);
  - приветственные баллы — через журнал, ключ `welcome:{membershipId}`:
    при вступлении или после первого чека.
- **Данные:** `Membership.tierManual boolean default false` (миграция).
- **API:**

  | Метод | Путь | Что |
  |---|---|---|
  | GET, PUT | `/v1/admin/settings/program/tiers` | `tiers`, `welcomeBonus` — отдельным входом (владелец) |
  | PUT | `/v1/admin/guests/{guestId}/tier` | `{ tierId: string \| null, reason }` — ручной статус; `null` — вернуть расчёт; аудит `GUEST_TIER_CHANGED` |
  | GET | `/v1/pos/guest` | + `tier { id, name, earnRate, redeemRate }` |
  | GET | `/v1/guest/…` карточка | + статус и сколько осталось до следующего |

- **Экран:** Настройки → «Программа»: лестница статусов (название, % начисления,
  % оплаты баллами, условие), скрытый статус, приветственные баллы. Карточка
  гостя: чип статуса и «Изменить статус». Касса: статус в карточке гостя.
- **Приёмка:** гость, перешедший порог суммы, на следующем чеке получает
  ставку нового статуса; ручной статус не слетает после чека.

### У4. Гости: список как у UDS, экспорт — СДЕЛАНО

> Сделано на сервере: фильтры `mode`, `tier`, `source`, `sleeping`, `buyers=none`
> (через «и»), в строке — статус, источник, дата вступления; выгрузка
> `POST /v1/admin/guests/export` — сразу файлом, телефоны маской, причина в аудите.
> Статусы пересчитываются у всех гостей сразу после правки лестницы. Сегменты RFM —
> вместе с отчётами (У8). На экране — фильтры в адресе страницы, колонки статуса,
> даты вступления и источника, выгрузка у владельца с причиной.

- **API:**

  | Метод | Путь | Что |
  |---|---|---|
  | GET | `/v1/admin/guests` | + фильтры `tier`, `source`, `tag`, `segment` (RFM), `buyers=none`; + колонки: оборот, баланс, статус, дата вступления, последний визит, источник |
  | POST | `/v1/admin/guests/export` | владелец; причина обязательна; аудит `DATABASE_EXPORTED`; телефоны — маской |

- **Экран:** таблица с колонками и чипами фильтров, счётчик «найдено N»,
  «Экспорт» с причиной.
- **Приёмка:** владелец находит «спящих резидентов со статусом Gold»
  и выгружает их без полных телефонов.

### У5. Карточка гостя: баллы вручную, заметки, теги — СДЕЛАНО

> Сделано на сервере: `POST /v1/admin/guests/{guestId}/points` — правка баланса
> владельцем через журнал (`ADJUST`), с причиной в аудите и ключом повтора, в минус
> не уходит; `PUT /v1/admin/guests/{guestId}/note` и заметка в карточке. Теги: справочник
> `/v1/admin/tags`, `PUT /v1/admin/guests/{guestId}/tags` набором целиком, фильтр списка
> `tag`.
>
> Экран: заметка и теги в карточке сразу под шапкой, тег заводится прямо из карточки;
> «Баллы вручную» у владельца — начислить или списать переключателем, один ключ повтора
> на одно намерение; справочник тегов в настройках; фильтр «Тег» в списке гостей.
> Отступление: вкладок в карточке нет — история одной лентой, как и была.

- **Данные:** `Tag` (заведение, название, цвет) и `GuestTag` (участие, тег) —
  RLS по заведению; `Membership.note text` (миграция).
- **API:**

  | Метод | Путь | Что |
  |---|---|---|
  | POST | `/v1/admin/guests/{guestId}/points` | `{ amount, reason }` со знаком, только владелец; журнал `ADJUST`; аудит `BALANCE_ADJUSTED`; `Idempotency-Key` обязателен |
  | PUT | `/v1/admin/guests/{guestId}/note` | `{ text }` до 1000 знаков |
  | GET, POST, PATCH, DELETE | `/v1/admin/tags` | справочник тегов |
  | PUT | `/v1/admin/guests/{guestId}/tags` | `{ tagIds }` |

- **Экран:** шапка карточки с действиями «Баллы», «Подарить», «Статус»;
  вкладки «Информация · Операции · Подарки · Рекомендации»; блоки заметок и тегов.
- **Приёмка:** правка баланса видна в журнале и аудите с причиной; повтор
  нажатия не удваивает.

### У6. Реферальная программа (уровень 1) — СДЕЛАНО

> Сделано на сервере: `GET /v1/guest/venues/{tenantId}/referral` — код приглашения
> (восемь знаков, выдаётся при первом открытии) и счётчики; `POST …/referral/accept` —
> друг становится гостем заведения «по приглашению»; награда пригласившему — подарком
> в журнал на первом чеке друга, ключ `referral:{участие друга}`, с лимитом и без
> контрольной группы; `GET, PUT /v1/admin/settings/program/referral`; блок `referral`
> в карточке гостя. Отступления: настройки — своим входом, как у статусов, а не полями
> `program-settings`; ссылка вида `?venue={tenantId}&ref={код}` — код уникален в пределах
> заведения. Условие статуса `REFERRALS` теперь считает только купивших друзей.
>
> Экран бэк-офиса: блок «Приглашения друзей» в настройках (включить, баллы за друга
> в батах, лимит наград) и в карточке гостя — кто его привёл и скольких привёл он.
>
> Приложение гостя: у заведения, где за друзей дают баллы, — «Пригласить друга» со ссылкой,
> кодом и счётчиками («поделиться» системным окном телефона или копированием); ссылка,
> открытая до входа, принимается сразу после входа, с ответом одной строкой над картой.

- **Механика:** у гостя — ссылка «пригласить друга» со своим кодом; друг,
  вступивший по ссылке, записывается в `referredById`; после его первого
  чека пригласивший получает баллы — через журнал, ключ
  `referral:{membershipId}`, `refType: referral`; лимит наград на гостя.
- **Данные:** внешний ключ и индекс на `Membership.referredById`, код
  приглашения на участии (миграция).
- **API:**

  | Метод | Путь | Что |
  |---|---|---|
  | GET | `/v1/guest/venues/{tenantId}/referral` | ссылка, приглашено, получено баллов |
  | вход гостя | `?ref=код` | привязка при вступлении |
  | GET, PUT | `/v1/admin/program-settings` | + `referral { enabled, reward, limit }` |

- **Экран:** гостевое приложение — «Пригласить друга»; карточка гостя —
  вкладка «Рекомендации»; Настройки → «Рефералы».
- **Приёмка:** друг по ссылке делает первый чек — пригласивший получает
  баллы ровно один раз; своя ссылка на себя не работает.

### У7. Источники трафика — СДЕЛАНО

> Сделано на сервере: справочник `/v1/admin/channels` (код ссылки выдаёт сервер, источник
> выключается, а не удаляется), `POST /v1/guest/venues/{tenantId}/join` — вступление
> по ссылке `?venue=…&src=…` с первым касанием, отчёт `/v1/admin/reports/channels?period` —
> вступили, впервые купили и выручка без отменённых чеков, отдельно гости без источника;
> источник в карточке гостя. У участия появилась дата вступления.
>
> Экран бэк-офиса: раздел «Отчёты» с отчётом «Источники» и блок «Источники трафика»
> в настройках с готовой ссылкой у каждого; источник в карточке гостя. Отступление:
> QR-код на экране не рисуется — ссылку копируют. Приложение гостя: ссылка источника,
> открытая до входа, запоминается и принимается сразу после входа, как приглашение друга.

- **Данные:** `AcquisitionChannel` (заведение, название, код, активен) —
  RLS; `Membership.channelId` (миграция).
- **API:**

  | Метод | Путь | Что |
  |---|---|---|
  | GET, POST, PATCH | `/v1/admin/channels` | справочник: табличка на столе, Instagram… |
  | GET | `/v1/admin/reports/channels?period` | клиенты · купили · выручка по источнику |
  | вход гостя | `?src=код` | привязка источника при вступлении |

- **Экран:** Настройки → «Источники» (ссылка для QR у каждого), Отчёты →
  «Источники».
- **Приёмка:** гость, вступивший по ссылке таблички, виден в строке источника
  вместе со своей выручкой.

### У8. Отчёты: клиенты, операции, RFM, сотрудники — СДЕЛАНО

> Сделано на сервере: `/v1/admin/reports/customers`, `/operations`, `/rfm`, `/staff` —
> отменённые чеки не считаются, выручка — деньгами. RFM — по порогам давности и частоты
> (а не по квантилям), десять сегментов; фильтр `segment` в списке гостей и выгрузке.
> Отступления: средняя оценка кассира — вместе с У10; «клиенты по уровням» — фильтром
> статуса в списке гостей (У4).
>
> Экран: раздел «Отчёты» вкладками, период в шапке, плитки и столбцы по дням;
> RFM-сегмент кликается и открывает «Гости» с фильтром «Сегмент».

- **API** (владелец и менеджер):

  | Метод | Путь | Что |
  |---|---|---|
  | GET | `/v1/admin/reports/customers?period` | всего, покупатели %, новые по дням, туристы/резиденты |
  | GET | `/v1/admin/reports/operations?period` | оборот, начислено, списано, средний чек, покупок, возвратов, график по дням |
  | GET | `/v1/admin/reports/rfm` | десять сегментов: покупателей, покупок, средний чек, оборот; считается по участиям на лету |
  | GET | `/v1/admin/reports/staff?period` | по кассиру: операций, оборот, новых гостей, средняя оценка (после У10) |

- **Экран:** раздел «Отчёты» с вкладками, фильтр периода, плитки с процентами,
  графики. RFM-сегмент кликается — открывает список гостей с этим фильтром.
- **Приёмка:** цифры отчётов сходятся с журналом (интеграционный тест на полигоне).

### У9. Сертификаты и день рождения — СДЕЛАНО

> Сделано на сервере: шаблоны `/v1/admin/certificates` со счётчиками «выдано / использовано»
> (акция вида `GIFT_CARD`), «Подарить» с `certificateId`; день рождения гостя
> `PUT /v1/guest/me/birthday` — один раз; подарок — баллы или сертификат — выдаётся сам
> при открытии кошелька и на кассе в окне ±N дней, ключ `birthday:{участие}:{год}`;
> настройки `/v1/admin/settings/program/birthday`. Отступление: настройки — своим входом,
> а не полями `program-settings`.
>
> Экран бэк-офиса: «Акции → Сертификаты», сертификат в «Подарить», блок «Подарок ко дню
> рождения» в настройках. Приложение гостя: вопрос «Когда у вас
> день рождения?» на карте — один раз, с подтверждением даты.

- **Механика:**
  - шаблон сертификата — номинал или подарок, срок; выдача — через «Подарить»,
    промокоды те же;
  - ко дню рождения — подарок из шаблона или баллы, выдаётся лениво: при
    открытии кошелька гостем или на кассе, в окне ±N дней, ключ
    `birthday:{membershipId}:{год}`.
- **API:**

  | Метод | Путь | Что |
  |---|---|---|
  | GET, POST, PATCH | `/v1/admin/certificates` | шаблоны; у каждого «выдано / использовано» |
  | POST | `/v1/admin/guests/{guestId}/gifts` | + `certificateId` |
  | GET, PUT | `/v1/admin/program-settings` | + `birthday { enabled, reward, daysBefore, daysAfter }` |

- **Приёмка:** гость с днём рождения завтра открывает кошелёк и видит подарок;
  повторное открытие второго не даёт.

### У10. Обратная связь — СДЕЛАНО

> Сделано на сервере: таблица `Review` с RLS (заведение — свои, гость читает свои и пишет
> только о своём чеке), `GET/POST /v1/guest/reviews` — «оцените визит» за 7 дней, один отзыв
> на чек, автоответ сразу; `GET /v1/admin/reviews` — сводка, распределение, темы и список
> с кассиром; `POST /v1/admin/reviews/{id}/reply`. Отступление: автоответы — вход
> `/v1/admin/settings/program/reviews`, как у дня рождения, а не `/v1/admin/review-settings`.
> Экран бэк-офиса: «Отзывы» — сводка, фильтры в адресе, ответ в один шаг; автоответы
> в настройках. Приложение гостя: «Как прошёл визит?» на карте и «Ответы заведений».

- **Данные:** `Review` (заведение, гость, чек, кассир, оценка 1–5, быстрые
  отзывы, текст, ответ, когда ответили, автоответ) — RLS: заведение читает
  свои, гость пишет и читает свои (миграция).
- **API:**

  | Метод | Путь | Что |
  |---|---|---|
  | POST | `/v1/guest/reviews` | оценка визита после чека: `{ ledgerEntryId, rating, tags, comment? }` — один отзыв на чек |
  | GET | `/v1/guest/reviews` | свои отзывы с ответами |
  | GET | `/v1/admin/reviews?rating&answered&period` | список, распределение, быстрые отзывы по темам |
  | POST | `/v1/admin/reviews/{id}/reply` | ответ владельца — виден гостю |
  | GET, PUT | `/v1/admin/review-settings` | автоответы по числу звёзд |

- **Экран:** гостевое приложение — «Оцените визит» после чека; бэк-офис —
  «Общение → Отзывы»: список слева, сводка справа, ответ в один шаг.
- **Приёмка:** гость ставит «2» с комментарием — владелец видит отзыв
  с кассиром, отвечает, гость видит ответ; автоответ приходит сразу.

### У11. «Сегодня» как у UDS — СДЕЛАНО

> Сделано на сервере: `GET /v1/admin/today` — выручка, покупки, средний чек, покупатели,
> новые и все гости, баллы, отмены за сутки по часам заведения и чеклист из четырёх шагов.
> Отступление: отдельный вход, а не `dashboard?period=today`. Экран: «Сегодня» над плитками «Обзора», карточки настройки у владельца.

- **API:** `GET /v1/admin/dashboard?period=today` — финансы, покупатели
  (всего, новые), операции (чеки, возвраты), плюс `setupChecklist`: программа
  настроена, есть кассир, есть акция, есть источник трафика.
- **Экран:** блоки дня и карточки «настройте за 5 минут» со ссылками
  в нужный раздел; карточка исчезает, когда шаг сделан.

### У12. Безопасность — СДЕЛАНО

> Сделано на сервере: `GET /v1/admin/security/history` — через функцию базы
> `tenant_audit_history` (миграция 20260916060000), без значений «было / стало»;
> `GET /v1/admin/security/suspicious` — гости выше порога чеков за день, кассиры

> Отступление: порог — своим входом, а не полем `program-settings`. Экран: блок в настройках и разбор `/settings/security` с двумя вкладками.

- **API:**

  | Метод | Путь | Что |
  |---|---|---|
  | GET | `/v1/admin/security/history?cursor` | история действий своего заведения — через функцию базы: роль приложения аудит не читает |
  | GET | `/v1/admin/security/suspicious?period` | гости с числом чеков за сутки выше порога, кассиры с всплесками |

- **Экран:** Настройки → «Безопасность»: условия кассы (номер чека, потолок —

### У13. Новости в приложении гостя — СЕРВЕР СДЕЛАН

> Сделано на сервере: таблица `News` с RLS (заведение — свои, гость — опубликованные

- **Данные:** `News` (заведение, заголовок, текст, опубликована) — RLS (миграция).
- **API:** `GET, POST, PATCH /v1/admin/news`;

- **Экран:** «Общение → Новости»; в приложении гостя — лента на карточке заведения.

## 4. Чего в этой очереди нет и почему

- **Рассылки и push, боты Telegram / MAX / VK** — нужны каналы и токены,
  которые выдаёт владелец. Энейблер из `09` (Срез 4).
- **Сгорание баллов** — нужен фоновый воркер (Э3): считать это на запросе
  значит однажды списать баллы посреди чека.
- **Товары, заказы, интернет-магазин** — живут в POSitive POS.
- **Многоуровневые рефералы, платное продвижение, AI-помощник** — не в этот заход.
