# Выкладка в интернет

Как перенести систему с вашего компьютера в интернет, чтобы она работала всегда и открывалась с телефонов.

Инструкция написана для человека, который не программист. Каждый шаг — что нажать и что должно получиться.

---

## Что куда едет

| Часть | Куда | Сколько стоит |
| --- | --- | --- |
| Бэк-офис (админка) | Cloudflare Pages | бесплатно |
| Страница гостя | Cloudflare Pages | бесплатно |
| Сервер (считает баллы) | Railway | от $5 в месяц |
| База данных | Supabase — уже настроена | по вашему тарифу |

**Порядок важен.** Сайты выкладываются первыми: сервер должен знать их адреса, иначе он не пустит браузер. Адреса заранее неизвестны — их выдаёт Cloudflare.

---

## Шаг 1. Админка на Cloudflare

1. Откройте [dash.cloudflare.com](https://dash.cloudflare.com) и войдите.
2. Слева выберите **Compute** → **Workers & Pages** → кнопка **Create** → вкладка **Pages** → **Connect to Git**.

   (В интерфейсе Cloudflare этот раздел лежит внутри **Compute**, отдельным пунктом меню его нет.)
3. Разрешите доступ к GitHub, выберите репозиторий **positive-loyalty**.
4. Заполните поля:

| Поле | Что вписать |
| --- | --- |
| Project name | `positive-admin` |
| Production branch | `main` |
| Framework preset | `None` |
| Build command | `pnpm run build:packages && pnpm --filter @positive/admin run build` |
| Build output directory | `apps/admin/dist` |
| Root directory | оставить пустым |

5. Раскройте **Environment variables** и добавьте:

| Имя | Значение |
| --- | --- |
| `NODE_VERSION` | `22.20.0` |
| `VITE_API_URL` | `https://placeholder.invalid/v1` |

`VITE_API_URL` пока временный: настоящий адрес сервера появится на шаге 3, и мы сюда вернёмся. Вписать что-то надо обязательно — иначе сборка пройдёт, а страница откроется **белой**: приложение проверяет адрес при запуске в браузере и без него падает сразу. Проверено чтением кода, не предположение.

`NODE_VERSION` обязателен: по умолчанию Cloudflare берёт версию старее той, что нужна проекту, и сборка падает с невнятной ошибкой.

6. **Save and Deploy**. Сборка идёт несколько минут.
7. Когда закончится, наверху будет адрес вида `https://positive-admin.pages.dev`. **Запишите его.**

Открыв его сейчас, вы увидите экран входа, но войти не получится — сервера ещё нет. Так и должно быть.

---

## Шаг 2. Страница гостя на Cloudflare

То же самое, но с другими значениями:

| Поле | Что вписать |
| --- | --- |
| Project name | `positive-guest` |
| Build command | `pnpm run build:packages && pnpm --filter @positive/guest run build` |
| Build output directory | `apps/guest/dist` |

Переменные те же: `NODE_VERSION=22.20.0` и временный `VITE_API_URL`.

Запишите второй адрес: `https://positive-guest.pages.dev`.

## Шаг 3. Сервер на Railway

### 3.1 Собрать настройки

На своём компьютере, в терминале, подставив **свои** два адреса из шагов 1 и 2:

```bash
pnpm setup:deploy https://positive-admin.pages.dev https://positive-guest.pages.dev
```

Команда создаст файл `.env.railway` рядом с проектом. В нём всё, что нужно серверу.

Она же проверит главное: что приложение будет ходить в базу **ограниченной ролью**, а не владельцем. Под владельцем изоляция заведений не действует, хотя выглядит настроенной, — и это единственная ошибка, которая обесценила бы всю защиту.

На экран ни одного пароля не выводится. Они только в файле, а файл в репозиторий не попадает.

### 3.2 Создать сервис

1. Откройте [railway.com](https://railway.com) → **New Project** → **Deploy from GitHub repo**.
2. Выберите **positive-loyalty**.
3. Railway начнёт собирать и, скорее всего, ошибётся — он не знает, что в репозитории несколько приложений. Это нормально, сейчас исправим.

### 3.3 Настроить сборку

Откройте созданный сервис → вкладка **Settings**:

| Поле | Что вписать |
| --- | --- |
| Root Directory | оставить пустым |
| Build Command | `pnpm run build:packages && pnpm --filter @positive/api run build` |
| Start Command | `pnpm --filter @positive/api run start` |
| Healthcheck Path | `/health` |

Порт вписывать не нужно: Railway задаёт его сам, а сервер его читает.

### 3.4 Вставить настройки

1. Вкладка **Variables** → кнопка **Raw Editor**.
2. Откройте файл `.env.railway` (он лежит в папке проекта), скопируйте **всё содержимое** и вставьте в окно.
3. **Save**. Сервис пересоберётся.

### 3.5 Получить адрес

Вкладка **Settings** → раздел **Networking** → **Generate Domain**.

Появится адрес вида `https://positive-loyalty-production-a1b2.up.railway.app`. **Запишите его.**

Проверьте, что сервер жив: откройте в браузере этот адрес и добавьте `/health`. Должно ответить `{"status":"ok",...}`.

## Шаг 4. Связать сайты с сервером

Теперь настоящий адрес сервера известен — впишем его в оба сайта.

Для **каждого** из двух проектов Cloudflare:

1. Откройте проект → **Settings** → **Environment variables** → **Production**.
2. Найдите `VITE_API_URL`, нажмите редактировать.
3. Впишите адрес сервера **с `/v1` на конце**:
   `https://ваш-адрес.up.railway.app/v1`
4. Сохраните.
5. Вкладка **Deployments** → на верхней записи меню «…» → **Retry deployment**.

Косая черта на конце не нужна: `.../v1`, а не `.../v1/`.

---

## Шаг 5. Проверить

Откройте `https://positive-admin.pages.dev` и войдите:

| Поле | Что вписать |
| --- | --- |
| Код устройства | `owner-kefir` |
| PIN | ваш |

Если вошло — готово. Система работает в интернете, и админка открывается с любого устройства.

## Шаг 6. Админка платформы — второй сервис

Это отдельный доступ владельца продукта: подписки, обороты по всем заведениям, партнёрства, акции. Он живёт **вторым сервисом рядом с первым**, а не внутри него.

### 6.1 Зачем отдельный сервис, а не ещё один экран

Обычный сервер видит только то заведение, чей токен предъявили, — так устроена сама база, а не проверка в коде. Панели платформы нужно противоположное: видеть всех сразу.

Дать это одному процессу означало бы, что владельцев ресторанов и владельца платформы обслуживает одно приложение с одними правами, и единственным, что отделяет ресторан от оборотов конкурента, остаётся правильно написанная проверка. Такие проверки в этом проекте уже ломались.

Поэтому граница проходит по учётным данным: у второго сервиса своя роль в базе, свой секрет подписи и **ни одного маршрута заведений**.

### 6.2 Собрать настройки

```bash
pnpm setup:deploy https://positive-loyalty.pages.dev https://positive-guest.pages.dev
```

Появятся **два** файла: `.env.railway` (первый сервис, как раньше) и `.env.railway.platform` (второй). Ни один в репозиторий не попадает.

### 6.3 Создать сервис

В **том же проекте** Railway, где уже стоит `positive-loyalty`:

1. Кнопка **+ Create** → **GitHub Repo** → снова **positive-loyalty**.
2. Дождитесь, пока Railway создаст второй сервис. Он соберётся неправильно — это нормально, сейчас настроим.
3. Переименуйте его: **Settings** → **Service Name** → `platform`. Иначе два сервиса будут называться одинаково, и однажды настройки уедут не туда.

### 6.4 Настроить сборку

Вкладка **Settings** у сервиса `platform`:

| Поле | Что вписать |
| --- | --- |
| Root Directory | оставить пустым |
| Build Command | `pnpm run build:packages && pnpm --filter @positive/api run build` |
| Start Command | `pnpm --filter @positive/api run start:platform` |
| Healthcheck Path | `/health` |

Отличие от первого сервиса ровно в одной строке — `start:platform` вместо `start`. Сборка общая, запускается другая точка входа.

### 6.5 Вставить настройки

**Variables** → **Raw Editor** → вставить **всё** содержимое `.env.railway.platform` → **Save**.

Проверьте, что вставили именно файл с `.platform` в имени. В нём намеренно **нет** `ACCESS_TOKEN_SECRET`: панели он не нужен, а его наличие позволило бы ей выписывать токены владельцев заведений.

### 6.6 Завести свою учётную запись

Пока в базе нет ни одного админа платформы, и войти некем.

```bash
pnpm --filter @positive/api build
node apps/api/dist/platform/bootstrap-admin.js "ваша@почта.рф" "Ваше Имя"
```

Скрипт напечатает пароль, ссылку для аутентификатора и десять кодов восстановления — **один раз и нигде не сохранит**. В базе останутся только отпечатки: восстановить исходные значения оттуда нельзя ни нам, ни тому, кто украдёт базу.

Что сделать сразу:

1. Пароль — в менеджер паролей.
2. Ссылку открыть на телефоне: аутентификатор (Google Authenticator, 1Password, любой) добавит строку с шестизначным кодом.
3. Коды восстановления распечатать и убрать **отдельно от пароля**.

### 6.7 Проверить

```bash
curl -s https://<адрес-сервиса-platform>/health
```

Ответ `{"status":"ok","service":"platform"}` означает, что второй сервис поднялся.

Первый вход **сам подтвердит** второй фактор: отдельного шага подтверждения нет и быть не может — чтобы до него добраться, надо войти, а вход требует кода. Круг разрывает сам сошедшийся код.

## Миграции базы: кто их применяет

**Railway перевыкатывает сервис на каждый push в `main`, но миграции сам
не применяет.** Это проверено на живом сервисе, а не предположено: 10 сентября
в бой уехал код с новой колонкой, которой не было в базе, и падало каждое
чтение журнала операций — при том, что `/health` продолжал отвечать `ok`.

Сейчас от этого защищают три вещи, и первые две пока не работают:

| Что | Состояние |
|---|---|
| `preDeployCommand` в `railway.json` | **не действует** — Railway не читает конфигурацию из репозитория для этих сервисов |
| Шаг миграций в деплое по тегу | работает, но нужны секреты `DATABASE_URL_PRODUCTION` / `DATABASE_URL_STAGING`, и деплой по тегу не используется |
| Отказ приложения стартовать | **работает** — API и панель не запускаются против базы, отставшей от кода |

### Конфигурация в репозитории сейчас игнорируется

В репозитории лежат `apps/api/railway.json` и `apps/api/railway.platform.json`,
но живые настройки сервисов им не соответствуют: в файлах указан сборщик
`NIXPACKS`, а сервисы собираются `RAILPACK`, и команда сборки отличается.
То есть файлы выглядят настройкой, а настройкой не являются — самый неприятный
вид документации.

Чтобы они заработали, в панели Railway у сервиса нужно заполнить поле
**Settings → Config as code** путём к файлу:

- сервис `positive-loyalty` → `apps/api/railway.json`
- сервис `platform` → `apps/api/railway.platform.json`

После этого выкатка начнёт сама применять миграции перед запуском нового кода.

### Пока это не сделано

Миграции применяются вручную, с рабочей машины, **до** влития кода:

```bash
pnpm db:deploy
```

Если про них забыть, новая версия просто не поднимется, а прежняя продолжит
работать: приложение сверяет список миграций, с которым собрано, с тем, что
применено в базе, и отказывается стартовать при расхождении. В логе Railway
это видно строкой от `[Migrations]`.

## Если что-то пошло не так

**Сборка на Cloudflare падает.** Чаще всего — не задан `NODE_VERSION`. Проверьте, что он равен `22.20.0`.

**Страница открывается белой, без ничего.** Не задан `VITE_API_URL`. Приложение проверяет адрес сервера при запуске и без него останавливается. Добавьте переменную и перезапустите выкладку.

**Админка открывается, но при входе пишет про сеть.** Сервер не пускает её адрес. Проверьте, что `CORS_ORIGINS` в Railway содержит ровно тот адрес, который в строке браузера, без косой черты на конце.

**Вход отвечает «не удалось войти».** Это ответ сервера, значит связь есть. Проверьте код устройства и PIN. После пяти неверных PIN вход блокируется на 15 минут.

**Сервер на Railway не поднимается.** Откройте вкладку **Deployments** → последний → **View logs**. Сообщение о нехватке переменной окружения означает, что настройки вставились не полностью — повторите шаг 3.4.

## Чего здесь пока нет

- **Фоновый обработчик** (`apps/worker`) — он рассылает уведомления и разгребает очередь. Ему нужен Redis (Upstash, бесплатный тариф). Без него система работает, но напоминания гостям не уходят.
- **Свой домен** вместо `pages.dev`. Подключается в Cloudflare за пару минут, но потребует поменять `CORS_ORIGINS` и `VITE_API_URL`.
- **Мобильные приложения**: пересобирать их не нужно. Адрес сервера в них настраивается на первом экране и хранится на самом устройстве, а значение из сборки — только подсказка по умолчанию (`apps/guest/src/shared/config/api-url.ts`). Достаточно один раз ввести боевой адрес в приложении.

  Это же значит, что переезд на свой домен позже обойдётся дёшево: поменять `CORS_ORIGINS`, `VITE_API_URL` и ввести новый адрес в приложениях. Пересборка APK не потребуется.
