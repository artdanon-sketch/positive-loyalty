## 1. Как мы ведём проект

### Принцип: вертикальные срезы, не слои

Не «сначала вся база, потом весь API, потом весь фронт». Каждая веха — **один сквозной путь, который работает от кассы до экрана владельца**. Так архитектурные ошибки вылезают на первой неделе, а не на третьем месяце.

Это же снимает главный риск вайбкодинга: когда сгенерирован большой слой, который ни с чем не соединён, проверить его нельзя, и он тихо накапливает ошибки.

### Роли двоих

Договоритесь письменно, кто за что отвечает финально. Не «мы оба всё» — при двух равных владельцах любого решения решения принимаются медленно.

Разумное разделение:
- **Один держит бэкенд и данные:** ledger, API, интеграция с POS, безопасность. Последнее слово по схеме базы.
- **Второй держит продукт и фронт:** экраны, дизайн-система, тексты, гостевое приложение. Последнее слово по интерфейсу.

Ревью взаимное, но право вето — у ответственного за область.

### Ветки и релизы

Trunk-based. `main` всегда деплоится. Ветки короткие, живут меньше двух дней.

```
main
 └─ feat/pos-webhook-receipt-closed
 └─ fix/ledger-serializable-retry
```

Каждый PR: описание что и зачем, скриншот для UI, зелёный CI. Мержим squash — история читаемая.

**Фича-флаги вместо длинных веток.** Неготовая функциональность едет в main выключенной. Флаги в базе, переключаются из админки платформы без деплоя.

### Спринт — неделя

Понедельник: разбор недели, три главные задачи, не больше.
Пятница: демо друг другу на staging. Не показали — не сделали.

Задачи в Linear или GitHub Projects. Формат задачи для Claude Code — важен:

> **Что:** обработчик вебхука `receipt.closed`
> **Зачем:** уровень L3, чек приходит из нашей кассы без участия человека
> **ТЗ:** `docs/02_API_контракты.md` раздел 4.1
> **Готово когда:** подпись проверяется, событие дедуплицируется, начисление создаётся идемпотентно, есть тест на повтор события, e2e зелёный

Плохая задача: «сделать вебхуки». Хорошая — та, у которой есть «готово когда».

## 2. Тестирование

Не гонимся за покрытием. Гонимся за тем, чтобы **ошибки в деньгах ловились автоматически**.

| Что | Чем | Обязательность |
|---|---|---|
| Ledger: идемпотентность, гонки, компенсации | vitest + реальная тестовая база | **обязательно** |
| Движок правил: применение и объяснение | vitest, табличные тесты | **обязательно** |
| Кросс-тенантный доступ по всем эндпоинтам | supertest | **обязательно** |
| Проверка подписи вебхука, replay | supertest | **обязательно** |
| Антифрод-детекторы | vitest на синтетике | **обязательно** |
| API happy path | supertest | по каждому эндпоинту |
| Экран кассы: скан → сумма → начисление | Playwright | **обязательно** |
| Остальной UI | Playwright по ключевым путям | выборочно |
| Компоненты | Storybook + снимки в обеих темах | выборочно |

**Тест на гонку баланса** — напиши его первым, до реализации:

```ts
it('два параллельных начисления не теряют одно из них', async () => {
  const key1 = randomUUID(), key2 = randomUUID()
  await Promise.all([
    ledger.earn({ membershipId, amount: 100, idempotencyKey: key1, ...ctx }),
    ledger.earn({ membershipId, amount: 200, idempotencyKey: key2, ...ctx }),
  ])
  const m = await prisma.membership.findUnique({ where: { id: membershipId } })
  const sum = await prisma.ledgerEntry.aggregate({ where: { membershipId }, _sum: { amount: true } })
  expect(m.pointsBalance).toBe(300)
  expect(sum._sum.amount).toBe(300)
})
```

Если он не проходит — вся остальная работа бессмысленна.

## 3. CI/CD

GitHub Actions. На каждый PR:

```yaml
jobs:
  check:
    steps:
      - lint
      - typecheck
      - gitleaks            # секреты
      - test:unit
      - test:integration    # поднимает postgres в сервисе
      - build
  preview:
    if: pull_request
    steps:
      - deploy api → Railway PR-окружение
      - deploy admin/guest → Cloudflare preview
      - test:e2e против preview
```

На `main`: тот же набор + деплой на staging. На тег `v*`: деплой на прод с ручным подтверждением.

**Миграции применяются отдельным шагом до деплоя кода** и должны быть обратимо совместимы — иначе откат кода при живой миграции ломает прод.

## 4. Дорожная карта: пять вертикальных срезов

Оценки — в неделях работы двух человек с Claude Code. Это оценка усилий, а не календарь: у вас есть основная работа.

### Срез 1. Скелет и сквозное начисление · 2–3 недели

**Цель:** гость сканирует QR, кассир вводит сумму, баллы ложатся в ledger, владелец видит операцию в списке.

- Монорепо, CI, окружения, деплой пустых приложений
- Prisma-схема: Tenant, Location, Staff, Guest, Membership, LedgerEntry, WebhookEvent, AuditLog
- RLS-политики и тест изоляции тенантов
- `LedgerService` с идемпотентностью и Serializable + тест гонки
- Auth: OTP для гостя, PIN для кассира
- `GET /pos/guest`, `POST /pos/transactions/preview`, `POST /pos/transactions/commit`
- Гостевое PWA: регистрация, кошелёк, экран QR (офлайн)
- Экран кассы: сканер, ввод суммы, подтверждение
- Бэк-офис: список операций и гостей, без графиков
- Seed с демо-данными

**Проверка среза:** на реальном телефоне сканируем код, на планшете начисляем, в бэк-офисе видим запись. Повторная отправка того же запроса не создаёт вторую операцию.

### Срез 2. Интеграция с POSitive POS · 2 недели

**Цель:** чек, закрытый в нашей кассе, начисляет баллы сам, без действий кассира.

- Событие `receipt.closed` на стороне POS (задача в репозиторий POS)
- `PosLink`, привязка мерчанта, генерация `webhookSecret`
- Обработчик вебхука: подпись, timestamp, дедупликация, очередь
- Обратный вебхук `guest.balance_changed`
- Показ баланса гостя на экране кассы POS
- Отмена: `receipt.voided` → `REVERSAL`

**Проверка:** закрываем чек в POS, ничего не нажимая в лояльности — баллы пришли, гость получил уведомление.

### Срез 3. Акции и конструктор · 3 недели

**Цель:** владелец за три тапа запускает акцию, гость её видит, кассир погашает.

- Модели Offer, OfferGrant
- Движок правил с приоритетами, стекированием и объяснением
- Шесть типов механик из ТЗ, включая штамп-карту с форой 2
- Конструктор в бэк-офисе: шаблоны, условия, живое превью, симуляция
- Выдача промокода по факту чека
- Погашение на кассе с атомарной проверкой
- Лента предложений в гостевом приложении

**Проверка:** запускаем «200 ฿ на завтра», оплачиваем чек 900 ฿, получаем код, на следующий день гасим его на кассе.

### Срез 4. Коммуникации и удержание · 2 недели

**Цель:** заведение может дотянуться до своих гостей бесплатно.

- Telegram-бот: привязка канала, уведомления, чат
- LINE OA: то же
- Wallet-пассы через провайдера, динамический баланс
- Рассылки: сегменты, превью, ограничение усталости, стоимость
- Автоматические сценарии: приветствие, реактивация, день рождения
- Отложенные начисления и сгорание баллов с уведомлениями

**Проверка:** отправляем спящим сегментом, сообщение приходит в Telegram и LINE, ограничение усталости срабатывает.

### Срез 5. Мотивация, антифрод, аналитика · 2–3 недели

**Цель:** владелец доверяет цифрам и видит, что программа работает.

- Мотивация персонала: конструктор, пять правил отклонения, дозревание
- Risk-модуль: шесть детекторов кассира, кластеризация устройств, градуированная реакция
- Дашборд: три плитки, график, живая лента через SSE, советы дня
- Контрольная группа и расчёт incremental revenue
- Отчёт по сотрудникам, лидерборд
- Ночная сверка баланса с алертом

**Проверка:** в демо-данных подложена накрутка — детектор её показывает. Incremental считается и не показывается при малой выборке.

## 5. Что делаем параллельно с кодом

Это не «потом», это в те же недели.

| Когда | Что | Кто |
|---|---|---|
| Неделя 1 | Партнёрское соглашение между вами двумя: доли, выход, права на код | оба |
| Неделя 1 | Решение по НДС: 690 ฿ с налогом или без — до публикации прайса | оба |
| Недели 1–3 | 15–20 интервью с владельцами по трём вертикалям | продуктовый |
| Недели 2–4 | Юрист: PDPA, статус баллов, структура владения | бэкенд |
| Недели 4–6 | Договорённость с 5–10 якорными заведениями на пилот | продуктовый |
| Постоянно | Проверенное восстановление из бэкапа раз в квартал | бэкенд |

Три из этих пунктов нельзя добавить задним числом: партнёрское соглашение, тайский язык в команде и контрольная группа. Остальное можно, но дороже.

## 6. Метрики, по которым понимаем, что идём правильно

**Продуктовые, смотрим еженедельно:**

| Метрика | Целевой ориентир |
|---|---|
| Доля чеков с программой в подключённых точках | ≥ 30% через месяц после подключения |
| Доля начислений уровня L2/L3 против ручного ввода | растёт квартал к кварталу |
| Доля точек с ≥10 начислениями в неделю | ≥ 70% — отличает «подключено» от «работает» |
| Доля гостей со вторым визитом за 30 дней | замерить на пилоте, потом растить |
| Завершаемость штамп-карт | ≥ 30% |
| Время от скана до начисления, p95 | < 5 с |

**Бизнесовые, смотрим ежемесячно:**

| Метрика | Почему она |
|---|---|
| **Survival rate через май–октябрь** | Главная метрика проекта. Без неё LTV/CAC = 0,7:1 |
| Конверсия Free → Pro | Рычаг сильнее цены: 25% → 45% меняет прибыль второго года с −328k до +45k |
| Новых заведений в месяц | Меньше 8 — проекта нет |
| Месячный отток | Выше 8% — модель не окупается |

**Точка решения о масштабировании:** не «100 заведений», а «100 заведений, из которых 60–70% пережили полный низкий сезон».

## 7. Главные риски исполнения

| Риск | Проявление | Что делаем |
|---|---|---|
| Сгенерированный код без ревью накапливает долг | Через месяц никто не понимает ledger | Железные правила в CLAUDE.md, обязательные тесты на деньги, взаимное ревью |
| Расползание объёма | «Давай ещё коалиционные баллы» на втором срезе | Срез закрыт — новые идеи в бэклог, не в текущий срез |
| POS не готов отдать событие чека | Срез 2 встаёт | Начать с задачи в репозитории POS на первой неделе, не на третьей |
| Тайский язык в поддержке | Не можем продать тайцу | Решить состав команды до первых продаж |
| Один из двоих выгорает | Проект встаёт целиком | Разделение областей ответственности, недельный ритм, письменные договорённости |

## 8. Первые три задачи для Claude Code

Начать буквально с них, в этом порядке.

**Задача 1. Монорепо и CI.**
Поднять pnpm workspaces со структурой из архитектуры, настроить lint, typecheck, vitest, GitHub Actions, деплой пустых приложений на Railway и Cloudflare. Готово, когда пустой PR проходит CI и превью-окружение поднимается автоматически.

**Задача 2. Ledger с идемпотентностью.**
Prisma-схема Tenant, Guest, Membership, LedgerEntry. `LedgerService` с методами `earn`, `redeem`, `reverse`. Serializable-транзакции с ретраем. Политики Postgres на запрет UPDATE/DELETE. Тесты: идемпотентность, гонка двух начислений, компенсация возврата, сверка кэша с суммой. Готово, когда все четыре теста зелёные.

**Задача 3. Изоляция тенантов.**
`TenantGuard` + `AsyncLocalStorage` + расширение Prisma. RLS-политики в миграции. Интеграционный тест, перебирающий эндпоинты с чужими идентификаторами. Готово, когда тест зелёный и падает при намеренном отключении гварда.

После этих трёх у вас есть фундамент, на котором остальное можно строить быстро и не бояться.
