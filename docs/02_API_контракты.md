# POSitive Loyalty — API-контракты

Версия 1.0 · для Claude Code

Базовый URL: `https://api.loyalty.positive.app/v1`
Формат: JSON, UTF-8. Все денежные суммы — **целые числа в минорных единицах** (сатанги). 690 ฿ = `69000`.

---

## 0. Общие правила

### Заголовки

| Заголовок | Когда | Что |
|---|---|---|
| `Authorization: Bearer <jwt>` | всегда, кроме публичных | access-токен, TTL 15 мин |
| `Idempotency-Key: <uuid>` | все мутирующие финансовые операции | обязателен, иначе `400` |
| `X-Request-Id: <uuid>` | желательно | сквозная трассировка в логах |
| `Accept-Language: ru\|en\|th\|zh` | опционально | язык сообщений об ошибках |

### Формат ошибки — единый

```json
{
  "error": {
    "code": "BALANCE_CHANGED",
    "message": "Баланс гостя изменился, пересчитайте preview",
    "details": { "expected": 42000, "actual": 38000 },
    "requestId": "0f4c…"
  }
}
```

`code` — машиночитаемый SCREAMING_SNAKE, стабильный контракт. `message` — человекочитаемый, локализованный, **не** для программной обработки.

### Коды состояния

`200` успех · `201` создано · `202` принято в обработку · `400` валидация · `401` нет токена · `403` роль не позволяет · `404` не найдено или чужой тенант · `409` конфликт состояния · `422` бизнес-правило не выполнено · `429` rate limit · `5xx` наша вина

**Важно:** чужой тенант отдаёт `404`, а не `403`. `403` подтверждает существование объекта и является утечкой.

### Идемпотентность

Ключ хранится 24 часа вместе с телом первого ответа. Повтор с тем же ключом возвращает **тот же ответ с тем же кодом**, а не создаёт новую операцию. Повтор с тем же ключом, но другим телом — `409 IDEMPOTENCY_KEY_REUSED`.

### Версионирование

Путь `/v1`. Реестр версий обязателен, устаревшие принудительно депубликуются. Ломающее изменение = новая версия, а не тихая правка.

### Health-check

Единственный эндпоинт **вне** префикса `/v1`: на него смотрит healthcheck Railway, и он не должен переезжать вместе с версией API. Токен не нужен.

```http
GET /health
```

```json
{
  "status": "ok",
  "service": "api",
  "version": "0.0.0",
  "uptimeSeconds": 42,
  "timestamp": "2026-08-25T07:00:00.000Z",
  "logins": { "google": true, "telegram": true, "phone": false }
}
```

Схема — `HealthResponse` в `packages/contracts/src/health.ts`, `.strict()`. `status` принимает единственное значение `ok`: сервис либо жив, либо не отвечает вовсе. `timestamp` в ISO-8601 — по нему видно, не отдаёт ли балансировщик кэш.

`logins` — какие способы входа **настроены на этом сервере**. Отдаются только имена и признак включённости, ни одного значения ключа.

Поле нужно по двум причинам. Первая: сервер намеренно отвечает одинаковым отказом на любую неудачу входа, и снаружи иначе не отличить «ключ не задан» от «токен плохой» — то есть нечем проверить, доехала ли настройка до боевого сервера. Вторая: гостевое приложение решает по этому полю, показывать ли кнопку. Кнопка без серверной половины гарантированно не работает, а гость, нажавший её, решает, что сломана вся программа.

## 1. Аутентификация

### 1.1 Гость: запрос кода

```http
POST /v1/auth/otp/request
Content-Type: application/json

{ "phone": "+66812345678", "tenantId": "3f2c…", "channel": "SMS" }
```

```json
{ "requestId": "b71e…", "expiresIn": 300, "resendAfter": 60 }
```

Rate limit: 3 запроса на номер за 10 минут, 20 на IP за час. Превышение — `429`.

При наличии Telegram или LINE канала у гостя `channel` может быть `TELEGRAM`/`LINE` — код уходит туда, и SMS не тратится. Экономия ощутима: SMS около 0,5 ฿ за штуку.

### 1.2 Гость: проверка кода

```http
POST /v1/auth/otp/verify
{ "requestId": "b71e…", "code": "418302" }
```

```json
{
  "accessToken": "eyJhbGciOi…",
  "refreshToken": "eyJhbGciOi…",
  "guest": { "id": "9c1a…", "displayName": null, "mode": "TOURIST", "locale": "ru" },
  "isNew": true
}
```

5 неверных попыток — блокировка `requestId`, `429`.

### 1.3 Гость: вход через аккаунт

Кода подтверждения здесь нет: личность уже подтвердил поставщик. Телефон не спрашивается — ни один из поставщиков его не отдаёт (docs/01, раздел 4.2).

Какие способы настроены на конкретном сервере, видно в `GET /health` → `logins`. Приложение читает это поле и не рисует кнопку, у которой нет серверной половины.

**Google — один шаг.** Страница получает токен от Google и приносит его нам:

```http
POST /v1/auth/social/google
{ "idToken": "eyJhbGciOiJSUzI1NiIs…" }
```

Ответ — тот же `GuestAuthResult`, что у проверки кода. Токен проверяется по открытым ключам Google: подпись, выпускающий, срок и то, что токен выписан **нашему** приложению. Любой отказ — один и тот же `401`: по разнице ответов удобно подбирать.

**Telegram — два шага, и это не усложнение ради усложнения.** Виджет Telegram привязан к домену, зарегистрированному у бота, а внутри мобильного приложения адрес страницы — `https://localhost`. Об эту стену уже разбился вход через Google в приложении. Здесь домен в обмене не участвует вовсе.

```http
POST /v1/auth/social/telegram/start
```

```json
{
  "requestId": "0f4c…",
  "claimSecret": "3Qm…",
  "url": "https://t.me/positive_loyalty_bot?start=AbC-123_xyz",
  "expiresIn": 300,
  "pollAfter": 2
}
```

Гость открывает `url`, нажимает в боте «Запустить», бот сообщает серверу, кто это. Приложение тем временем спрашивает результат:

```http
POST /v1/auth/social/telegram/claim
{ "requestId": "0f4c…", "claimSecret": "3Qm…" }
```

```json
{ "state": "PENDING", "session": null }
```

```json
{ "state": "READY", "session": { "accessToken": "…", "refreshToken": "…", "expiresIn": 900, "guest": { … }, "isNew": true } }
```

Отвечает всегда `200`: «ещё нет» — нормальный ход обмена, а не ошибка.

`claimSecret` обязателен и решает главное: подтверждение приходит **не от того**, кто спрашивает результат. Без секрета сессию забрал бы любой, кто узнал `requestId`, — а `requestId` не секрет. Сессия выдаётся ровно один раз; повтор получает `EXPIRED`.

`EXPIRED` возвращается на три разные причины — нет такой попытки, не тот секрет, вышел срок — и различить их снаружи нельзя намеренно.

Ограничения: 10 начатых входов с адреса за 10 минут; ссылка живёт 5 минут; `/start` принимается только в личной переписке — иначе бота добавляют в группу, пишут туда чужой код из ссылки и подтверждают чужой вход.

### 1.4 Сотрудник и владелец

Владелец — через OAuth POSitive POS (см. архитектуру, 3.1). Сотрудник — по PIN на выданном устройстве:

```http
POST /v1/auth/staff/pin
{ "locationId": "…", "pin": "4821", "deviceId": "…" }
```

`deviceId` обязателен и должен быть заранее зарегистрирован владельцем. PIN без привязки к устройству не принимается — иначе кассир зайдёт с домашнего телефона и начислит себе.

### 1.5 Обновление токена

```http
POST /v1/auth/refresh
{ "refreshToken": "…" }
```

Refresh **ротируется**: старый инвалидируется. Повторное использование отозванного refresh — `401` + алерт в risk-модуль + отзыв всей цепочки сессий этого субъекта.

## 3. POS API — самое горячее место

Отдельный неймспейс `/v1/pos/*`. Авторизация — токен сотрудника либо сервисный токен кассы.

### 3.0 Правила кассы

```http
GET /v1/pos/config
```

```json
{ "requireReceiptNumber": true, "maxManualAmount": 300000, "allowManualEntry": true }
```

Экран кассы запрашивает это ДО ввода суммы. Иначе поле номера чека подписано «необязательно», кассир его пропускает, а сервер отвечает `RECEIPT_REQUIRED` — при госте, который стоит у стойки. Отказывать за то, что мы и так знали, нельзя.

Наружу уходят только правила кассира из `ProgramConfig.cashierRules`. Ставки начисления, лестница статусов и мотивация персонала остаются в бэк-офисе: касса ими не распоряжается, а лишние поля в ответе — лишняя поверхность.

### 3.0.1 Виды продаж заведения


### 3.3 Проведение

```http
POST /v1/pos/transactions/commit
Idempotency-Key: 8d1f0a2c-…

{ "previewId": "pv_8f2a…", "receiptId": "pos_rcpt_99182", "paidBy": "PROMPTPAY", "saleKindId": "3f0c…" }
```

```json
{
  "transactionId": "tx_5c9…",
  "redeemed": 20000,
  "earned": 12000,
  "newBalance": 34000,
  "grantsIssued": [
    { "grantId": "bb22…", "title": "Вернём 200 ฿", "code": "KATA-200-9K2P", "expiresAt": "2026-08-19T23:59:59+07:00" }
  ],
  "stamps": { "current": 5, "target": 12 },
  "staffReward": null,
  "guestNotified": ["TELEGRAM", "WALLET"]
}
```

**Повтор чека.** Ключ идемпотентности — `receiptId`, а не заголовок: касса,
потерявшая связь, часто шлёт повтор с новым `Idempotency-Key`, а чек тот же.

Повтор проверяется ПЕРВЫМ, до любой проверки состояния, и возвращает `200`
с первым ответом и `replayed: true`. Ни `PREVIEW_EXPIRED`, ни `BALANCE_CHANGED`
на повторе не возникают: состояние, на которое они смотрят, изменил сам первый
вызов. Ответ на повтор совпадает с первым во всём, кроме `replayed`, — в том
числе если касса пересчитала предрасчёт и прислала другой `previewId`.

```json
{ "transactionId": "tx_5c9…", "redeemed": 20000, "earned": 12000, "newBalance": 34000, "replayed": true }
```

Ошибки, которые касса обязана уметь показать:

| Код | Когда | Что делать кассе |
|---|---|---|
| `PREVIEW_EXPIRED` | прошло больше 10 минут | перезапросить preview |
| `BALANCE_CHANGED` | гость потратил баллы в другом месте | перезапросить preview, показать новую сумму |
| `LIMIT_REACHED` | превышен лимит кассира по операциям в час | предупредить менеджера |
| `AMOUNT_ABOVE_CAP` | сумма выше `maxManualAmount` | позвать менеджера |
| `RECEIPT_REQUIRED` | не передан `receiptNumber` при включённом правиле | попросить ввести номер чека |
| `TENANT_MISCONFIGURED` | настройки заведения не проходят проверку контракта | чек не провести, звать поддержку — чинится в настройках, а не на кассе |
| `SALE_KIND_NOT_FOUND` | вид продажи чужой или выключен | перезапросить список видов |

**Вид продажи (`saleKindId`) — необязателен.** Это ответ на вопрос «что продали»:
абонемент, разовое занятие, аренда на неделю. Список ведёт само заведение
(раздел 5.7), кассир выбирает из готового.

Не путать с `refType`. Тот отвечает, ЧЕМ вызвана запись журнала (чек, промокод,
реферал), и участвует в отмене чека и в отчётах по выручке. Записать вид продажи
туда значило бы, что отмена абонемента перестала находить свои строки, а выручка
перестала считать эту продажу выручкой.

Ради вида продажи и заводился справочник: партнёрское условие «купил абонемент —
получи ролл в подарок» (docs/07) на одной сумме не строится — ужин на 5 000 ฿
и абонемент на 5 000 ฿ для журнала неотличимы.

Чужой или выключенный вид отвергается ДО записи: внешний ключ подтвердил бы
существование строки, потому что проверка ссылочной целостности идёт от имени
системы и политики изоляции обходит.

### 3.4 Погашение ваучера

```http
POST /v1/pos/grants/redeem

{ "code": "KATA-200-9K2P", "receiptId": "pos_rcpt_99183" }
```

```json
{
  "grantId": "aa11…",
  "code": "KATA-200-9K2P",
  "offerId": "of_1",
  "title": "Ролл Филадельфия в подарок",
  "redeemedAt": "2026-09-11T14:22:00.000Z",
  "replayed": false
}
```

`title` — что именно отдать гостю. `null`, если у акции нет названия: кассиру
это честнее пустой строки, а выдачу подарка отсутствие текста блокировать
не должно.

**Проверки по порядку:** код существует → `state = ISSUED` → не истёк → тенант
совпадает → окно по времени суток выполняется. Первая непройденная возвращает
свой код ошибки — `GRANT_NOT_FOUND`, `GRANT_ALREADY_USED`, `GRANT_EXPIRED`,
`GRANT_WRONG_TENANT`, `GRANT_OUT_OF_WINDOW`.

Коды доходят до кассы как есть: кассир должен понимать, что сказать гостю.
«Код уже погашен», «срок истёк» и «не то время суток» — три разных разговора.

**Погашение атомарно:** `UPDATE OfferGrant SET state='REDEEMED' WHERE id=…
AND state='ISSUED'` с проверкой, что изменилась ровно одна строка. Без этого
два кассира погасят один код одновременно.

**Повтор того же чека возвращает первый ответ** с `replayed: true`, а не отказ
«код уже погашен». Железное правило 3, и причина та же, что на проведении чека:
касса, потерявшая связь уже после успешного погашения, при повторе решила бы,
что операция не прошла, — и подарок гостю не отдала, хотя код в базе сгорел.

Ключом служит `receiptId`, а не заголовок `Idempotency-Key`: касса, потерявшая
связь, шлёт повтор с новым заголовком, но с тем же чеком.

**Без `receiptId` повтор идемпотентным не будет** — сопоставить его не с чем,
и второй запрос получит `GRANT_ALREADY_USED`. Поле необязательно намеренно:
гость может предъявить код до заказа, когда чека ещё нет.

**Чужой код неотличим от несуществующего** — в бою оба дают `GRANT_NOT_FOUND`.
Приложение ходит в базу ролью, для которой политика изоляции не отдаёт чужую
строку вовсе, и это правильно: иначе касса превратилась бы в способ проверять,
какие акции идут у соседа.

`GRANT_WRONG_TENANT` остаётся в перечне ради честного контракта, но достижим
только там, где чтение идёт без изоляции — например, под ролью владельца базы
в тестовой оснастке. Касса этот код в бою не увидит.

**На экране кассы** — панель «Погасить промокод»: для кассира, а менеджеру
и владельцу — когда касса не справилась. Код нормализуется (пробелы долой,
буквы заглавные). Если номер чека не введён, экран подставляет сгенерированный
и держит его до успеха — повтор после обрыва связи идемпотентен. Без связи
код не гасится: подарок, в отличие от чека, в очередь не откладывают.
К каждому коду отказа экран добавляет подсказку, что сказать гостю.

### 3.5 Отмена

```http
POST /v1/pos/transactions/{transactionId}/void
Idempotency-Key: …
{ "reason": "WRONG_AMOUNT", "comment": "пробили 1200 вместо 120" }
```

Создаёт `REVERSAL`-записи, возвращает списанные баллы, аннулирует выданные ваучеры, снимает штамп, отменяет награду сотруднику. Окно отмены для кассира — 15 минут, дальше только менеджер и только с комментарием. Всё пишется в `AuditLog`.

Повтор отмены, как и повтор чека, проверяется до прав и до окна: если компенсации
уже созданы, ответ — `200` с прежними `reversals` и `replayed: true`. Кассир,
отменивший чек на четырнадцатой минуте и потерявший связь, не получит
`VOID_WINDOW_EXPIRED` на повторе за работу, которая уже сделана.

Планшет присылает **снимок** своей очереди отложенных чеков — целиком,
а не изменения. Чего нет в снимке, из очереди ушло: строка помечается снятой
и не удаляется. Пустой список — «у меня ничего не лежит».

- **Сервер по снимку ничего не проводит.** Проведёт планшет тем же ключом
  идемпотентности, когда появится связь: две очереди с правом проводить
  однажды провели бы чек дважды.
- **Телефон хранится только маской** — «+66 •• •• 4821».
- **Метка планшета случайная**, создаётся в браузере один раз: устройства
  в токене нет.
- Изменения очереди уходят сразу, тот же снимок — не чаще раза в пять минут.
  Шлёт любой, кто за кассой; до 200 чеков.

причина в нём, — или **убрать** после подтверждения. Повтор идёт тем же ключом
идемпотентности. Убранный чек пропадает и у владельца со следующим снимком.

## 4. Вебхуки от POSitive POS

### 4.1 Чек закрыт

```http
POST /v1/webhooks/pos/receipt-closed
X-Positive-Signature: sha256=9f86d0…
X-Positive-Timestamp: 1755500000
X-Idempotency-Key: pos_rcpt_99182
```

```json
{
  "event": "receipt.closed",
  "occurredAt": "2026-08-18T19:31:07+07:00",
  "posMerchantId": "pm_4471",
  "posLocationId": "pl_02",
  "receipt": {
    "id": "pos_rcpt_99182",
    "number": "A-10493",
    "total": 120000,
    "currency": "THB",
    "paidBy": "PROMPTPAY",
    "closedAt": "2026-08-18T19:31:05+07:00",
    "cashierId": "emp_18",
    "loyalty": { "guestToken": "gt_v1.eyJ…", "previewId": "pv_8f2a…" },
    "items": [ { "sku": "tomyum", "qty": 1, "price": 32000 } ]
  }
}
```

Блок `loyalty` присутствует, если гостя идентифицировали на кассе. Если его нет — событие всё равно обрабатывается: оно нужно для статистики «доля чеков с программой», которая и есть главная метрика проникновения.

Проверка подписи:

```ts
const base = `${timestamp}.${rawBody}`
const expected = crypto.createHmac('sha256', link.webhookSecret).update(base).digest('hex')
if (!crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(received))) throw new UnauthorizedException()
if (Math.abs(Date.now()/1000 - Number(timestamp)) > 300) throw new UnauthorizedException()
```

`timingSafeEqual` — обязательно. Обычное `===` даёт timing-атаку.

**Что реализовано и чем отличается от наброска выше:**

- Подписывается `<timestamp>.<сырое тело>`. Метка времени входит в подписываемое: иначе записанный запрос переигрывается с любой свежей меткой, и проверка окна становится украшением.
- Подпись считается по **сырым байтам**, а не по разобранному и снова собранному JSON: другой порядок ключей или другие пробелы — и хеш не сойдётся. В NestJS для этого включён `rawBody: true`.
- Окно времени **двустороннее**: часы отправителя могут и спешить. Односторонняя проверка пропустила бы запрос, датированный будущим.
- Формат подписи проверяется **до** сравнения: `timingSafeEqual` бросает на буферах разной длины, и незамеченное исключение дало бы `500` вместо `401` — заодно рассказав отправителю, что его подпись хотя бы дошла до сравнения.
- Ответ на все причины отказа **один и тот же**. По разнице сообщений иначе видно, существует ли заведение и какой проверки не хватило.
- Время закрытия чека приходит местным со смещением (`…+07:00`) и приводится к UTC **на границе**: журнал принимает одно каноническое представление. Послаблять контракт журнала нельзя — два вида записи одного момента разъедутся при первом сравнении дат.

Ответ на принятое событие:

```json
{ "eventId": "3f1d5b7a-…", "duplicate": false }
```

Код ответа — `202`, а не `200`: «событие принято», а не «баллы начислены». Повтор с тем же `X-Idempotency-Key` тоже отвечает `202`, но с `duplicate: true` и тем же `eventId` — повтор это нормальная работа кассы с плохой связью, а не ошибка.

**Дедупликация двухступенчатая.** `X-Idempotency-Key` не даёт завести второе событие; ключ журнала по номеру чека (`pos:earn:<receipt.id>`) не даёт начислить дважды, даже если касса пересобрала событие и прислала его с новым ключом.

**Чек без блока `loyalty` — не ошибка.** Событие принимается и помечается `SKIPPED`: оно нужно ради доли чеков с программой.

**Очередь живёт в таблице `WebhookEvent`, а не в Redis.** Если писать строку в базу И класть задачу в очередь, появляются два независимых хранилища и две новые поломки: строка без задачи — событие принято и потеряно; задача без строки — дедупликация не сработала, чек начислен дважды. Приём обязан быть одной транзакцией. Когда обработку понадобится разнести по процессам, воркер будет разбирать ту же таблицу: строки со статусом `PENDING` никуда не денутся.

### 4.3 Исходящие вебхуки к POS

Мы тоже отправляем события — чтобы касса показывала актуальный баланс:

- `guest.balance_changed` — баланс изменился вне кассы
- `offer.granted` — гостю выдан ваучер, который можно погасить у этого мерчанта

Подписываем тем же способом. Повторы: 5 попыток с задержкой 1с, 5с, 30с, 5м, 30м.

**Что реализовано.** `guest.balance_changed` — из событий этого раздела; `offer.granted` приедет вместе с движком акций.

```http
POST <PosLink.callbackUrl>
X-Positive-Signature: sha256=…
X-Positive-Timestamp: 1755500000
```

```json
{
  "event": "guest.balance_changed",
  "eventId": "3f1d5b7a-…",
  "occurredAt": "2026-08-27T15:12:04.000Z",
  "guestId": "20000000-…",
  "balance": 45325,
  "delta": 4400
}
```

Решения, которые стоит знать:

- **Событие выводится из журнала, а не пишется рядом с ним.** Очевидный ход — писать строку доставки в той же транзакции, что и операцию, — гарантию даёт, но требует, чтобы `LedgerService` знал про кассу: где взять адрес, каким ключом подписать, слать ли вообще. Ядро начало бы зависеть от прикладного модуля. Журнал уже append-only и долговечен, поэтому разгребатель сам находит операции, о которых касса ещё не знает. Цена — событие уходит не мгновенно, а в ближайший проход.
- **Событие может уйти дважды**, и `eventId` в теле нужен затем, чтобы касса дедуплицировала у себя. «Ровно один раз» через сеть не гарантируется в принципе; гарантируется «не меньше одного» плюс способ отличить повтор.
- **О своих же чеках кассе не рассказывают.** Операции с источником `POS_WEBHOOK` пропускаются: касса о них знает, а лишнее событие — повод рассинхронизироваться.
- **Историю не выгружаем.** Операции старше момента подключения кассы и старше суток не отправляются. `balance_changed` — подсказка для показа, а не источник истины: актуальный баланс касса и так спросит при опознании гостя. Без этой границы подключение кассы к работающему заведению отправляло бы ей месяцы неактуальных уведомлений.
- **В событии нет ни имени, ни телефона** — только идентификатор гостя и суммы. Всё остальное касса знает про своего гостя сама (железное правило 5).
- **Момент решения один на весь проход.** И выборка «кому пора», и расчёт следующей паузы берут одно и то же время, переданное снаружи. Иначе расписание повторов считается от одного момента, а выборка идёт по другому — и сдвиг часов между процессом и базой превращается в повторы не тогда, когда задумано.

## 5. Бэк-офис: заведение

### 5.1 Дашборд

```http
GET /v1/admin/dashboard?period=7d
```

```json
{
  "guestsViaProgram": { "value": 147, "prev": 124, "changePct": 18.5, "newGuests": 38 },
  "pointsLiability": { "value": 1240000, "prev": 1198000 },
  "topOffer": { "offerId": "of_1", "title": "200 ฿ на завтра", "redeemed": 64, "returnedGuests": 41 },
  "series": [ { "date": "2026-08-12", "new": 3, "returning": 14 } ],
  "hourly": [ { "hour": 10, "guests": 12 } ],
  "incremental": { "programAvgCheck": 72000, "controlAvgCheck": 61000, "upliftPct": 18.0, "controlSize": 62 }
}
```

`pointsLiability` — «я должен баллами». Формулировка в интерфейсе именно такая: это обязательство бизнеса, а не абстрактная цифра.
`incremental` считается по контрольной группе. Если контрольная группа меньше 30 человек, поле не возвращается — статистики нет, и врать нельзя.

**Что отдаёт реализация сейчас** (`period` принимает `7d | 30d | 90d`, по умолчанию `7d`; неизвестное значение — `400 VALIDATION_FAILED`, а не молчаливый откат):

```json
{
  "period": "7d",
  "guestsViaProgram": { "value": 147, "prev": 124, "changePct": 18.5, "newGuests": 38 },
  "pointsLiability": { "value": 1240000, "prev": 1198000 },
  "series": [ { "date": "2026-08-12", "new": 3, "returning": 14 } ],
  "hourly": [ { "hour": 10, "guests": 12 } ],
  "incremental": { "programAvgCheck": 72000, "controlAvgCheck": 61000, "upliftPct": 18.0, "controlSize": 62 },
  "advice": [ { "kind": "SLEEPING_GUESTS", "guests": 26 } ],
  "isPartialPeriod": false,
  "isEmpty": false
}
```

Отличия от примера выше и их причины:

- `topOffer` не отдаётся: сущности `Offer` ещё нет. Плитка с придуманной акцией на главном экране хуже, чем две плитки вместо трёх.
- `advice` — блок «Что стоит сделать сегодня» (docs/03, раздел 2). **Сервер отдаёт повод и числа, а не готовый текст:** продукт четырёхъязычный, строки живут в JSON фронта. Пороги при этом остаются на сервере — это бизнес-правила, и в компоненте им не место. Выдаются `STUCK_RECEIPTS` — первым, если с планшетов не дошёл хоть один чек (`{ "kind": "STUCK_RECEIPTS", "receipts": 3 }`, раздел 3.6), — затем `PARTNERS_WAITING` — входящие приглашения и условия, ждущие ответа (`{ "kind": "PARTNERS_WAITING", "invites": 1, "terms": 2 }`), — `EXPIRING_GIFTS` — от трёх выданных и непогашенных подарков, срок которых кончится в ближайшие 7 дней (`{ "kind": "EXPIRING_GIFTS", "gifts": 12, "withinDays": 7 }`), — `PARTNER_RECIPROCATE` — разные гости партнёра за 30 дней погасили у нас не меньше 10 подарков, а ответного условия от партнёра нет (`{ "kind": "PARTNER_RECIPROCATE", "partnershipId": "…", "partnerName": "Dance Studio Kata", "guests": 12 }`), — `SLEEPING_GUESTS`, `QUIET_HOURS`, `MANUAL_ENTRY`; поводы «точка без QR» и «акция кончается» ждут сущностей `Location` и `Offer`. Максимум три совета; пустой список означает «блок скрыть целиком», а не «всё хорошо».
- `changePct` равен `null`, когда в прошлом периоде ноль: делить не на что, а «+100%» здесь было бы приукрашиванием.
- `isPartialPeriod` — заведение моложе периода: экран прячет дельты и помечает график «данных пока мало».
- `isEmpty` — ни одного оформленного гостя: вместо плиток показывается онбординг-чеклист.

Дельта всегда считается к ПРЕДЫДУЩЕМУ отрезку той же длины, а не к календарной неделе: иначе цифра зависела бы от того, в какой день владелец открыл экран.

Все границы суток и часы считаются в `Tenant.timezone`. «С 14 до 17 зал пустой» — это местное время заведения, а не UTC.

### 5.1.1 Живая лента

```http
GET /v1/admin/stream        (text/event-stream)
```

```
data: {"id":"d333f83e-…","kind":"ledger.earned","masked":"A***","amount":2250,"basis":45000,"at":"2026-08-27T13:28:26.597Z"}
```

Права те же, что у дашборда: менеджер и владелец. Кассиру — `403`.

Имя приходит **только маскированным**: лента висит на экране в зале. Полного имени в ответе нет вовсе — маскирование на клиенте было бы украшением, а не защитой.

Заведение берётся из токена в момент подписки и замыкается на всё время жизни потока: читать его из контекста запроса внутри обработчика нельзя, поток переживает запрос.

Каждые двадцать секунд уходит служебное событие-сердцебиение. Клиент его игнорирует; оно нужно, чтобы прокси не закрыл молчащее соединение.

### 5.2 Гости

```http

```

Недавние визиты первыми. `q` — одна строка поиска до 64 знаков; пустая означает
«без поиска». Человек у стойки не выбирает, по какому полю искать, — он повторяет
то, что сказал гость. Гость попадает в выдачу, если совпало хоть что-то:

| Что набрали | Как ищется |
|---|---|
| имя или его часть | вхождение без учёта регистра |
| номер чека | точное совпадение с номером на операции |
| от четырёх цифр телефона | по концу номера; пробелы, скобки и плюс не мешают |
| промокод | точное совпадение среди подарков **этого** заведения, регистр не важен |

Три цифры по телефону не ищут: такое совпадение есть у каждого тысячного номера.

### 5.2.1 Подарок гостю

```http
POST /v1/admin/guests/{guestId}/gifts
Idempotency-Key: 0f6c2d9e-5b1a-4c3e-9d7f-2a8b4c6d1e3f

{ "title": "Десерт", "reason": "LONG_WAIT", "validityDays": 14 }
```

```json
{
  "grantId": "71717171-7171-4717-8717-717171717171",
  "title": "Десерт",
  "codeTail": "Q7XR",
  "expiresAt": "2026-09-29T12:00:00.000Z",
  "replayed": false
}
```

Спор у стойки решается на месте: менеджер дарит гостю промокод, и тот сразу
появляется у гостя в приложении. Гасится на кассе, как любой другой, и виден
в истории гостя.

- **Причина обязательна**: `LONG_WAIT` · `STAFF_ERROR` · `COMPLAINT` ·
  `CELEBRATION` · `OTHER` — для `OTHER` нужен `comment`. Причина пишется
  в аудит (`GIFT_ISSUED`) вместе с тем, кто подарил.
- **`Idempotency-Key` обязателен.** Повтор с тем же ключом возвращает тот же
  подарок (`replayed: true`), второй не выдаётся. Тот же ключ для другого гостя —
  `409`.
- **Кода целиком в ответе нет** — только `codeTail`: код у гостя в приложении.
- Под подарком — акция вида `GOODWILL` на одного гостя. Это не кампания:
  в списке акций и отчётах её не будет.
- **Менеджер — не больше 20 подарков за сутки** на всё заведение, владелец —
  без ограничения. Отступление от `docs/05` («акции — только владелец») —
  осознанное: подарок одному гостю у стойки не кампания, а менеджер там,
  где владельца нет.

| Код | Статус | Когда |
|---|---|---|
| `IDEMPOTENCY_KEY_REQUIRED` | 400 | нет заголовка или он пустышка |
| `VALIDATION_FAILED` | 400 | нет названия, причины или комментария к «другой» |
| `FORBIDDEN` | 403 | кассир |
| `NOT_FOUND` | 404 | гость не участвует в программе этого заведения |
| `GIFT_LIMIT` | 409 | менеджер: за сутки уже 20 подарков |
| `IDEMPOTENCY_KEY_REUSED` | 409 | этим ключом уже подарили другому гостю |

PIN и его хеш не отдаются никогда и ни в каком виде.

```http
POST /v1/admin/staff

```

```json
{ "staff": { "id": "c3d2…", "displayName": "Нок", "role": "CASHIER", "…": "…" }, "deviceCode": "pos-m3x8vd" }
```

Сотрудник заводится вместе с первым устройством. **Код устройства** — то, что он
введёт на экране входа вместе с PIN. Сам по себе не секрет: без PIN бесполезен.

Роли — только `CASHIER` и `MANAGER`. Владелец не заводит других владельцев:
передача заведения — событие другого масштаба, чем «сменить PIN».

PIN — от 4 до 6 цифр, не из очевидных (`1234`, `0000`, …). Это не делает четыре цифры
стойкими; PIN защищают привязка к устройству и блокировка после серии неудач.
Запрет нужен против другого: «1111», выданный кассиру, через неделю знает вся смена.

```http
PATCH /v1/admin/staff/b2c1…

{ "isActive": false }
```

**Отключение режет доступ сразу**, а не когда истечёт восьмичасовой токен. Для этого
сотрудник сверяется с базой на каждом запросе: middleware читает его строку и кладёт
в контекст **живую** роль. Отключённый получает `401`, как с просроченным токеном;
его сессии отозваны, обновить их нельзя.

**Смена роли действует без повторного входа** — по той же причине. Повышенного кассира
не выкидывает из системы посреди смены, а понижённый менеджер теряет права сразу.

```http
POST /v1/admin/staff/b2c1…/pin

{ "pin": "7942" }
```

Снимает блокировку после неудачных попыток и **отзывает все сессии**: PIN меняют
и тогда, когда его узнал чужой.

| Код | Когда |
|---|---|
| `VALIDATION_FAILED` | неверное имя, роль или слишком простой PIN — сообщение объясняет словами |
| `FORBIDDEN` | запрос не от владельца |
| `OWNER_NOT_MANAGED` | попытка изменить владельца из списка команды |
| `NOT_FOUND` | сотрудника нет в этом заведении — ответ тот же, что для чужого |

**Мотивация персонала** — ещё не реализована:

```http

PUT  /v1/admin/settings/staff-reward
{ "enabled": true, "basis": "PER_NEW_GUEST", "value": 2000, "vesting": "ON_SECOND_VISIT", "shiftCap": 15 }
```


### 5.6 Настройки программы

**Только владелец.** Процент начисления — деньги заведения: менеджер, способный
поднять его себе в смену, раздавал бы чужую выручку баллами.

```http
GET /v1/admin/settings/program
```

```json
{
  "baseEarnRate": 5,
  "baseRedeemRate": 20,
  "cashierRules": { "requireReceiptNumber": true, "maxManualAmount": null, "allowManualEntry": true }
}
```

```http
PUT /v1/admin/settings/program

{
  "baseEarnRate": 7,
  "baseRedeemRate": 30,
  "cashierRules": { "requireReceiptNumber": true, "maxManualAmount": 300000, "allowManualEntry": false }
}
```

**Отступление от первоначального замысла.** Раньше здесь было написано «тело =
`ProgramConfig` целиком». Принимаются только три настройки — **те, что касса уже
соблюдает**: процент начисления, доля оплаты баллами и правила ввода на кассе.
Режим «скидка», срок жизни баллов, приветственные баллы и статусы описаны
в `ProgramConfig`, но механики под ними нет. Сохранить их через этот вход нельзя —
`.strict()` отвергает лишнее поле: переключатель, который ничего не делает, хуже
отсутствующего. Они появятся здесь вместе со своими механиками.

**Три поля заменяются целиком, остальное не трогается.** Статусы и приветственные
баллы, заведённые при подключении, сохранением этого экрана не стираются.
В базу пишется сырой объект с подмешанными полями, а не разобранный конфиг —
иначе туда уехали бы сегодняшние значения по умолчанию для полей, которых
владелец не касался.

**Итог проверяется той же схемой, по которой читает касса.** Сохранить то, на чём
касса упадёт на следующем чеке, нельзя: отказ приходит владельцу сейчас,
а не кассиру в час пик.

Касса применяет новые значения **со следующего чека**. Изменение пишется в аудит
с тем, что было, и тем, что стало.

| Код | Когда |
|---|---|
| `VALIDATION_FAILED` | процент вне диапазона, лишнее поле, потолок не в целых сатангах |
| `FORBIDDEN` | запрос не от владельца |
| `TENANT_MISCONFIGURED` | сохранённые настройки не читаются — чинит поддержка, а не владелец |

### 5.8 Партнёрства: договориться

Замысел целиком — `docs/07`, раздел 9. Здесь то, что уже работает.

**Смотреть — владелец и менеджер. Договариваться — только владелец.** Принятое
условие рождает акцию заведения, а создавать акции по матрице прав `docs/05`
может только он.

Чужое партнёрство — `404`, даже по точному id: по ответу нельзя узнать, что два
других заведения о чём-то договариваются.

ресторану проще договориться со спа, чем с другим рестораном. Заблокированные

#### Приглашение

```http

{
  "partnerTenantId": "22222222-2222-4222-8222-222222222222",
  "text": "Мы студия танцев через дорогу, у нас двести учеников в месяц. Давайте дружить."
```

```json
  "quota": { "freeLimit": 3, "freeUsed": 1, "freeLeft": 2 }

```

| Код | Статус | Когда |
|---|---|---|
| `VALIDATION_FAILED` | 400 | текст короче 40 знаков |
| `SELF_INVITE` | 400 | приглашение самим себе |
| `PARTNER_NOT_FOUND` | 404 | такого открытого заведения в сети нет |
| `BLOCKED_BY_RECIPIENT` | 403 | получатель не принимает приглашения от вас |
| `INVITES_SUSPENDED` | 403 | пять неразобранных жалоб «спам» — приглашать нельзя до разбора платформой |
| `PARTNERSHIP_EXISTS` | 409 | с этим заведением уже идёт разговор; `details.partnershipId` |
| `INVITE_COOLDOWN` | 409 | вам отказали меньше 30 дней назад; `details.retryAfter` |
| `PARTNERSHIP_LIMIT` | 409 | действующих партнёрств уже максимум |
| `INVITE_QUOTA_EXCEEDED` | 402 | бесплатные приглашения на сегодня закончились |

- **Одна пара — одно партнёрство, в обе стороны.** Встречное приглашение
  отбивается, даже отправленное в ту же секунду.
- **Квота списывается последней.** Приглашение, отбитое по любой другой
  причине, бесплатного не тратит.
- **Сутки — по часам заведения**, а не сервера.
- Месяц тишины — только для того, кому отказали. Отказавший может передумать
  и пригласить сам, сразу.
- **Автоохлаждение.** Три отказа от разных заведений за неделю — тридцать дней
  от третьего отказа одно бесплатное приглашение в сутки. Блокировка входящего
  приглашения — тоже отказ. Лишнее приглашение получает `INVITE_QUOTA_EXCEEDED`
  с `details.coolingUntil`.
- **Приостановка.** Пять неразобранных жалоб «спам» от разных заведений —
  `INVITES_SUSPENDED`, пока платформа не разберёт. Кто пожаловался и сколько
  было жалоб, обвинённый не узнаёт.

```http
GET /v1/admin/partnerships/quota
```

```json
{
  "freeLimit": 1,
  "freeUsed": 0,
  "freeLeft": 1,
  "restriction": { "kind": "COOLING", "until": "2026-10-15T12:00:00.000Z" }
}
```

`restriction` — `null`, `{ "kind": "COOLING", "until": "…" }` или
`{ "kind": "SUSPENDED" }`; при приостановке `freeLimit` равен нулю.

#### Список и карточка

```http
GET /v1/admin/partnerships?status=ACTIVE
```

Сначала то, что ждёт нашего ответа, в конце — завершённое.

```http

```

```json
  "proposedAt": "2026-09-14T09:00:00.000Z",
```

#### Действия

```http
POST /v1/admin/partnerships/{id}/accept                      приглашённый: «обсудить»
POST /v1/admin/partnerships/{id}/decline   { "reason"?: "…" } приглашённый: отказать
POST /v1/admin/partnerships/{id}/end       { "reason"?: "…" } любая сторона: расторгнуть
POST /v1/admin/partnerships/{id}/block     { "reason"?: "…", "spam"?: true } любая сторона: навсегда
POST /v1/admin/partnerships/{id}/messages  { "text": "…" }    после принятия
```

Каждое действие отвечает карточкой партнёрства; сообщение — самим сообщением.

- **Расторжение:** новые подарки прекращаются сразу, выданные промокоды
  действуют до своего срока — погашение смотрит на промокод, а не на акцию.
- **Блокировка:** живое приглашение закрывается, действующее партнёрство
  расторгается. Заблокированный получает `BLOCKED_BY_RECIPIENT` — без причины.
- **Жалоба «спам»** — `spam: true` в блокировке, и только на приглашение, которое
  ждёт вашего ответа: иначе «спам» стал бы оружием в споре бывших партнёров.
  Входящее приглашение, закрытое блокировкой, — отказ для охлаждения отправителя.
  Платформе уходит событие `INVITE_SPAM_REPORTED` в аудит.
- **Писать** можно после принятия приглашения: до него отправитель заваливал бы
  получателя сообщениями без его согласия.

| Код | Статус | Когда |
|---|---|---|
| `NOT_FOUND` | 404 | партнёрства нет, или заведение в нём не участвует |
| `NOT_RECIPIENT` | 403 | на приглашение отвечает не приглашённый |
| `PARTNERSHIP_STATE` | 409 | приглашение уже не ждёт ответа, партнёрство уже завершено, жалоба не на ждущее ответа приглашение |

#### Условия

```http
GET  /v1/admin/partnerships/{id}/sale-kinds                виды продаж обеих сторон
POST /v1/admin/partnerships/{id}/terms                     предложить
POST /v1/admin/partnerships/{id}/terms/{termId}/accept     принять — у дающего подарок появится акция
POST /v1/admin/partnerships/{id}/terms/{termId}/reject     отклонить чужое или отозвать своё
POST /v1/admin/partnerships/{id}/terms/{termId}/pause      приостановить
POST /v1/admin/partnerships/{id}/terms/{termId}/resume     снять паузу
```

Головной пример `docs/07`, раздел 4.3 — ресторан дарит ролл гостям студии
за абонемент:

```http
POST /v1/admin/partnerships/{id}/terms

{
  "direction": "WE_GIVE",
  "trigger": { "type": "ON_SALE_KIND", "saleKindId": "3f0c…", "minAmount": 500000 },
  "reward": { "kind": "FREE_ITEM", "itemName": "Ролл Филадельфия", "minCheck": 80000 },
  "validityDays": 14,
  "limits": { "totalGrants": 200, "perGuest": 1, "dailyCap": 10 }
}
```

Каждое действие отвечает карточкой партнёрства; условия лежат в `terms` —
так их видит студия после принятия:

```json
{
  "id": "…",
  "direction": "THEY_GIVE",
  "status": "ACTIVE",
  "trigger": { "type": "ON_SALE_KIND", "saleKindId": "3f0c…", "minAmount": 500000 },
  "reward": { "kind": "FREE_ITEM", "itemName": "Ролл Филадельфия", "minCheck": 80000 },
  "validityDays": 14,
  "limits": { "totalGrants": 200, "perGuest": 1, "dailyCap": 10 },
  "saleKindName": "Абонемент на месяц",
  "proposedByUs": false,
  "acceptedAt": "2026-09-14T11:20:00.000Z",
  "pausedByUs": false,
  "grantsIssued": 12,
  "grantsRedeemed": 7,
  "actions": { "accept": false, "reject": false, "pause": true, "resume": false }
}
```

- **Направление словами**: `WE_GIVE` — подарок даём мы гостям партнёра,
  `THEY_GIVE` — партнёр нашим. В условие нельзя вписать третье заведение.
- **Только то, что сработает.** Триггеры: `ON_PURCHASE`, `ON_SALE_KIND`,
  `ON_FIRST_VISIT`, `ON_NTH_VISIT`, `ON_MEMBERSHIP`. Подарки: `FREE_ITEM`,
  `PERCENT_OFF`, `FIXED_OFF` — их кассир отдаёт по коду. Штампы, статусы
  и начисление баллов при погашении — `400`: механики под ними нет.
- **Вид продаж** обязан принадлежать заведению, где покупают, и быть включённым.
  Название приходит в `saleKindName`: соглашаются на «абонемент», а не на id.
- **Принятое условие рождает акцию** у дающего подарок — `visibility: PARTNER`,
  тексты для гостя и кассира собирает сервер: «Ролл Филадельфия в подарок»,
  «К заказу от 800 ฿», «Подарок от партнёра — …». Партнёрство становится
  `ACTIVE`. Повторное, в том числе одновременное, принятие второй акции
  не создаёт.
- **Пауза** — любая сторона, без объяснений: новые подарки не выдаются,
  выданные действуют. **Снять паузу может только поставивший.**
- **Цифры** `grantsIssued` и `grantsRedeemed` считаются по промокодам и видны
  обеим сторонам. Ни кодов, ни гостей — только числа.
- Правки действующего условия нет: предложите новое и приостановите старое.

| Код | Статус | Когда |
|---|---|---|
| `VALIDATION_FAILED` | 400 | триггер или подарок без механики, срок вне 1–90 дней |
| `SALE_KIND_NOT_FOUND` | 400 | вид продаж не того заведения или выключен |
| `NOT_COUNTERPARTY` | 403 | условие принимает тот, кто его предложил |
| `NOT_PAUSER` | 403 | паузу снимает не тот, кто её поставил |
| `TERM_NOT_FOUND` | 404 | такого условия в этом партнёрстве нет |
| `TERM_STATE` | 409 | условие уже не ждёт ответа, не действует или не на паузе |
| `PARTNERSHIP_STATE` | 409 | приглашение ещё не принято или партнёрство завершено |

**Отступления от `docs/07`.** Условие адресуется направлением, а не парой
`triggerTenantId`/`rewardTenantId`. Появился `accept` — в замысле «Обсудить» есть
в схеме, но не в API. Расторжение не ждёт семь дней: новые подарки прекращаются
сразу, а «догорание» — это срок уже выданных промокодов. Платных приглашений
сверх квоты и перевода переписки пока нет — сообщения хранятся с языком
оригинала, переводчик сядет на это поле.

## 6. Админка платформы

Отдельный неймспейс `/v1/platform/*`, отдельная роль, отдельный контур входа с обязательной 2FA.

```http
GET  /v1/platform/tenants?status=TRIAL&cursor=…
POST /v1/platform/tenants/{id}/impersonate     → короткоживущий токен, всегда в AuditLog
GET  /v1/platform/metrics                       → MRR, churn, survival rate через низкий сезон
POST /v1/platform/moderation/reviews/{id}       → скрыть отзыв
GET  /v1/platform/risk/alerts                   → лента подозрительной активности по всем тенантам
```

`impersonate` — самая опасная ручка в системе. Требования: только роль `PLATFORM_ADMIN`, обязательная причина текстом, TTL 30 минут, баннер «вы смотрите как владелец» в интерфейсе, запись в аудит и уведомление владельцу на почту.

#### Жалобы на спам в приглашениях — работает

```http
GET  /v1/platform/invite-complaints
POST /v1/platform/invite-complaints/{tenantId}/review
```

```json
{
  "items": [
    {
      "tenantId": "…",
      "brandName": "Phuket Ride",
      "openComplaints": 5,
      "suspended": true,
      "lastComplaintAt": "2026-09-15T12:00:00.000Z",
      "complaints": [
        {
          "fromTenantId": "…",
          "fromBrandName": "Kata Beach Kitchen",
          "reason": "Рассылка всем подряд",
          "createdAt": "2026-09-15T12:00:00.000Z"
        }
      ]
    }
  ],
  "suspendAfter": 5
}
```

- Жалобы считаются по разным заведениям; приостановленные — первыми.
- **Имя жалобщика и причина — только здесь.** Обвинённое заведение видит лишь,
  что приглашения приостановлены (раздел 5.8).
- `review` отмечает неразобранные жалобы на заведение и снимает приостановку:
  `{ "tenantId": "…", "reviewed": 5 }`. Повтор отвечает `reviewed: 0` без второй
  записи в аудите. В аудит — `INVITE_COMPLAINTS_REVIEWED`.
- Отказы разбор не трогает: охлаждение за три отказа за неделю — отдельное правило.
- На странице панели — секция «Жалобы на спам в приглашениях» с кнопкой «Разобрано»;
  когда жалоб нет, секции нет.

## 7. Rate limiting

| Эндпоинт | Лимит |
|---|---|
| `POST /auth/otp/request` | 3 / номер / 10 мин · 20 / IP / час |
| `POST /auth/otp/verify` | 5 попыток на requestId |
| `POST /pos/transactions/commit` | 60 / кассир / час (настраивается) |
| `POST /pos/grants/redeem` | 30 / кассир / час |
| `GET /guest/*` | 120 / гость / мин |
| `POST /admin/broadcasts` | 10 / тенант / сутки |
| Остальные | 600 / токен / мин |

Ответ `429` с заголовком `Retry-After`. Счётчики в Redis, ключ включает субъект, а не только IP — иначе один отель с NAT заблокирует всех своих гостей.

## 8. Что должно быть в Swagger

NestJS + `@nestjs/swagger`, схемы генерируются из zod через `nestjs-zod`. Требования:

- Каждый эндпоинт имеет пример запроса и ответа — тот же, что в этом документе.
- Каждый код ошибки перечислен в `@ApiResponse`.
- Публичная документация для POS-интеграции выкладывается отдельным статическим сайтом: партнёрам и своей же кассе нужен читаемый контракт, а не догадки.
