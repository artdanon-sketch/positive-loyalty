# POSitive Loyalty — архитектура и модель данных

Версия 1.0 · для Claude Code · август 2026

---

## 1. Контекст

**POSitive POS** — существующий продукт: касса и бэк-офис для заведений.
NestJS (Node + TypeScript), PostgreSQL через Prisma, база на Supabase, API на Railway, фронт React 18 + Vite на Cloudflare Pages, планшетная касса завёрнута в Capacitor.

**POSitive Loyalty** — новый продукт: программа лояльности. Тот же стек, та же семья, общий бренд.

### Почему это стратегически важно

Ресерч показал: в этой нише выживают те, кто врос в кассу или в платёж. Fivestars продан SumUp за $317 млн, Punchh — PAR за $500 млн; Shopkick и Bink, жившие «поверх» чужих касс, умерли. Мы владеем кассой — значит уровень начисления **L3 (сумму подтверждает система, а не человек)** доступен нам из коробки для собственных мерчантов. Это то, чего UDS не может: он всегда гость в чужой кассе.

Из этого следует главное архитектурное решение: **Loyalty — отдельный сервис со своей базой, но с привилегированным каналом к POS.** Не модуль внутри POS и не полностью независимый продукт.

## 3. Связь с POSitive POS

Три канала, каждый со своей задачей.

### 3.1 Идентичность: POS как провайдер входа

У владельца заведения не должно быть двух логинов. POS выступает OAuth2-провайдером, Loyalty — клиентом.

```
Владелец → loyalty-admin → «Войти через POSitive»
  → api.positive-pos/oauth/authorize?client_id=loyalty&scope=merchant.read
  → callback с кодом → loyalty-api меняет код на токен
  → получает {pos_account_id, pos_merchant_ids[], email, name}
  → находит или создаёт Tenant, связывает pos_merchant_id ↔ tenant_id
```

Таблица связи обязательна и заполняется один раз при подключении:

```prisma
model PosLink {
  id            String   @id @default(uuid())
  tenantId      String
  posMerchantId String   @unique   // id заведения в POSitive POS
  posLocationId String?             // id точки, если их несколько
  webhookSecret String               // HMAC-ключ для вебхуков от POS
  linkedAt      DateTime @default(now())
  tenant        Tenant   @relation(fields: [tenantId], references: [id])
  @@index([tenantId])
}
```

`Задача для Claude Code:` если POS ещё не умеет отдавать OAuth — на первом этапе делаем ручную привязку по API-ключу, а OAuth выносим отдельной задачей. Интерфейс `PosIdentityProvider` пишем сразу, чтобы подмена была одной строкой.

### 3.2 Начисление: вебхук от кассы

Это главный канал. Касса закрыла чек — Loyalty узнаёт об этом сразу и без участия человека.

```
POS: чек закрыт
  → POST https://api.loyalty.positive.app/v1/webhooks/pos/receipt-closed
     X-Positive-Signature: sha256=<hmac>
     X-Positive-Timestamp: 1755500000
     X-Idempotency-Key: <pos_receipt_uuid>
```

Тело события — в документе API-контрактов, раздел 4.1.

**Требования к обработчику, нарушать нельзя:**

1. Проверка HMAC-подписи по `webhookSecret` конкретного `posMerchantId`.
2. Проверка `timestamp` с допуском 5 минут — защита от повторной отправки.
3. Дедупликация по `X-Idempotency-Key` в таблице `WebhookEvent` с UNIQUE.
4. Обработка асинхронная: эндпоинт кладёт событие в очередь и отвечает `202` не дольше чем за 200 мс. Касса не должна ждать нашу бизнес-логику.
5. Ответ `2xx` не означает «баллы начислены» — означает «событие принято». Результат касса узнаёт обратным вызовом или запросом статуса.

### 3.3 Списание: синхронный вызов из кассы

Когда гость хочет **оплатить баллами**, касса обязана дождаться ответа — иначе она не знает итоговую сумму. Здесь синхронный двухфазный протокол.

```
1. Кассир сканирует QR гостя
   POS → GET /v1/pos/guest?token=<qr>          ~50 мс
   ← {guestId, name, balance, tier, availableOffers[]}

2. Кассир нажимает «применить баллы»
   POS → POST /v1/pos/transactions/preview      ~80 мс
        {guestId, amount, items[]}
   ← {maxRedeemable, pointsToEarn, appliedOffers[], previewId}

3. Гость подтвердил, чек закрывается
   POS → POST /v1/pos/transactions/commit       ~100 мс
        {previewId, receiptId} + Idempotency-Key
   ← {transactionId, redeemed, earned, newBalance}
```

`preview` ничего не меняет в ledger и живёт 10 минут. `commit` идемпотентен по ключу. Между ними баланс блокируется мягко: если гость параллельно потратил баллы в другом заведении, `commit` вернёт `409 BALANCE_CHANGED` и касса перезапросит `preview`.

### 3.4 Обратный канал: баланс на экране кассы

POS показывает баланс гостя прямо в чеке. Реализуется тем же `GET /v1/pos/guest`. Кэшировать на стороне POS не дольше 30 секунд.

**Про `isControlGroup`.** При создании Membership с вероятностью 5% ставим `true`. Такие гости регистрируются, видят карту, но **баллы им не начисляются** и они это видят («вы в группе сравнения, программа скоро включится»). Без этого невозможно доказать владельцу, что программа работает, а не что гости пришли бы и так. Задним числом это не восстанавливается — поэтому в MVP, а не потом.

### 4.4 Ledger — сердце системы

```prisma
model LedgerEntry {
  id             String     @id @default(uuid())
  tenantId       String
  guestId        String
  membershipId   String

  type           LedgerType                     // EARN | REDEEM | EXPIRE | ADJUST | REVERSAL | GRANT
  amount         Int                            // ЗНАКОВОЕ: +начисление, −списание
  balanceAfter   Int                            // снапшот для быстрых выписок

  basisAmount    Int?                           // сумма чека в минорных единицах
  currency       String     @default("THB")

  source         LedgerSource                   // POS_WEBHOOK | POS_SYNC | SIGNED_QR | STAFF_MANUAL | PAYMENT | SYSTEM
  refType        String?                        // receipt | offer_grant | referral | promo
  refId          String?

  idempotencyKey String     @unique
  reversalOfId   String?    @unique             // компенсирующая запись
  offerId        String?

  actorType      ActorType                      // SYSTEM | STAFF | OWNER | GUEST
  actorId        String?
  locationId     String?
  deviceId       String?
  ip             String?

  createdAt      DateTime   @default(now())

  @@index([tenantId, createdAt])
  @@index([membershipId, createdAt])
  @@index([guestId, createdAt])
}
```

**Правила работы с ledger — это не рекомендации.**

1. Записи только добавляются. `UPDATE` и `DELETE` на этой таблице запрещены на уровне политики Postgres.
2. `Membership.pointsBalance` — денормализованный кэш. Пишется только в той же транзакции, что и ledger-запись. Ночной джоб сверяет кэш с суммой и алертит на расхождение.
3. Отмена операции создаёт запись `REVERSAL` со ссылкой `reversalOfId`, а не правит исходную.
4. Каждая запись обязана иметь `idempotencyKey`. Для вебхука POS это `pos_receipt_id`, для подписанного QR — `nonce`, для ручного ввода — UUID, сгенерированный кассой до отправки.
5. Все денежные величины — целые в минорных единицах. Никаких float.

Пример правильной записи начисления:

```ts
// apps/api/src/core/ledger.service.ts
async earn(input: EarnInput): Promise<LedgerEntry> {
  return this.prisma.$transaction(async (tx) => {
    const existing = await tx.ledgerEntry.findUnique({
      where: { idempotencyKey: input.idempotencyKey },
    })
    if (existing) return existing            // повтор — возвращаем первый результат

    const m = await tx.membership.findUniqueOrThrow({
      where: { id: input.membershipId },
      select: { pointsBalance: true, tenantId: true, guestId: true },
    })
    const balanceAfter = m.pointsBalance + input.amount

    const entry = await tx.ledgerEntry.create({
      data: { ...input, balanceAfter, type: 'EARN' },
    })
    await tx.membership.update({
      where: { id: input.membershipId },
      data: {
        pointsBalance: balanceAfter,
        visitsTotal: { increment: 1 },
        spentTotal: { increment: input.basisAmount ?? 0 },
        lastVisitAt: new Date(),
      },
    })
    return entry
  }, { isolationLevel: 'Serializable' })
}
```

`Serializable` здесь обязателен: два параллельных начисления на один membership без него дадут потерянное обновление.

### 4.5 Акции и правила

```prisma
model Offer {
  id          String      @id @default(uuid())
  tenantId    String
  type        OfferType   // CASHBACK | PROMO_ON_CHECK | FLASH_1DAY | TIME_WINDOW |
                          // STAMP_CARD | NETWORK_VOUCHER | REFERRAL | BIRTHDAY |
                          // WINBACK | PACKAGE | GIFT_CARD
  status      OfferStatus @default(DRAFT)       // DRAFT | SCHEDULED | LIVE | PAUSED | ENDED
  priority    Int         @default(100)         // порядок применения в движке правил
  stackable   Boolean     @default(false)       // можно ли складывать с другими

  audience    Json                              // ALL | TOURIST | RESIDENT | NEW | SLEEPING | segmentId
  schedule    Json                              // {startsAt, endsAt, weekdays[], timeWindow{from,to}}
  limits      Json                              // {totalQty, perGuestQty, minCheck, maxDiscount}
  reward      Json                              // {kind, value}
  visibility  Visibility  @default(VENUE_ONLY)  // VENUE_ONLY | NETWORK
  i18n        Json                              // {ru:{title,desc},en:{...},th:{...},zh:{...}}

  createdAt   DateTime    @default(now())
  grants      OfferGrant[]
  @@index([tenantId, status])
}

model OfferGrant {
  id            String      @id @default(uuid())
  offerId       String
  guestId       String
  code          String      @unique             // ≥8 символов, криптостойкий
  state         GrantState  @default(ISSUED)    // ISSUED | REDEEMED | EXPIRED | VOID
  issuedAt      DateTime    @default(now())
  expiresAt     DateTime
  redeemedAt    DateTime?
  redeemedBy    String?
  nonce         String      @unique
  @@index([guestId, state])
  @@index([offerId, state])
}
```

**Движок правил.** При каждом `preview` собираем применимые акции, сортируем по `priority`, применяем по очереди. Нестекируемая акция обрывает цепочку. Результат — объяснимый список: что применилось и почему. Это важно и для интерфейса кассы, и для разбора спорных случаев.

### 4.7 Прочие модели

- `Staff` — сотрудник: роль (`CASHIER | MANAGER | OWNER`), pin-код, привязка к точкам, телефон и device fingerprint для антифрод-связки.
- `Consent` — согласия PDPA: версия текста, время, канал, IP. Неизменяемая.
- `Device` — отпечатки устройств гостя для выявления ферм аккаунтов.
- `WebhookEvent` — входящие события с `externalId UNIQUE`, статусом и числом попыток.
- `AuditLog` — все действия в бэк-офисе: кто, что, старое значение, новое, IP. Хранение 24 месяца.
- `Broadcast` / `BroadcastRecipient` — рассылки и их доставка.
- `Certificate` — сертификаты и абонементы.
- `Review` — отзывы и оценки.

## 5. Мультитенантность

Два рубежа, оба обязательны.

**Рубеж 1 — приложение.** `tenantId` берётся **только из JWT**, никогда из тела запроса или query. В NestJS это `TenantGuard`, который кладёт `tenantId` в `AsyncLocalStorage`, и расширение Prisma, автоматически подставляющее `where: { tenantId }` во все запросы.

```ts
// apps/api/src/common/prisma-tenant.extension.ts
export const tenantExtension = Prisma.defineExtension((client) =>
  client.$extends({
    query: {
      $allModels: {
        async $allOperations({ model, operation, args, query }) {
          const tenantId = tenantStore.getStore()?.tenantId
          if (!tenantId || GLOBAL_MODELS.has(model)) return query(args)
          if (READ_OPS.has(operation)) {
            args.where = { ...args.where, tenantId }
          }
          return query(args)
        },
      },
    },
  })
)
```

**Рубеж 2 — база.** Row Level Security в Postgres на всех тенантных таблицах. Приложение выставляет `SET LOCAL app.tenant_id` в начале транзакции. Даже если в коде забудут фильтр, база не отдаст чужое.

```sql
ALTER TABLE "LedgerEntry" ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "LedgerEntry"
  USING ("tenantId" = current_setting('app.tenant_id', true));
```

`Задача для Claude Code:` написать интеграционный тест, который под токеном тенанта A пытается прочитать и записать данные тенанта B по прямому id — во всех эндпоинтах. Тест обязан быть в CI и падать красным при регрессии.

## 8. Что взяли у конкурентов и что сознательно не взяли

### Взяли у UDS (проверено в живом кабинете)

| Механика | Как у них | Как у нас |
|---|---|---|
| Два режима программы | «Понижать сумму счёта» или «Начислять баллы» | То же, поле `mode` |
| Статусы клиентов | Название, % начисления, % списания, условия перехода по сумме покупок и рекомендациям | То же + условие по числу визитов |
| Скрытый статус | Назначается вручную, другим не виден | То же, флаг `hidden` |
| Приветственные баллы | После вступления или после первой покупки | То же |
| Отдельный % списания | Ограничивает, какую долю чека можно закрыть баллами | То же |
| Обязательный номер чека | Кассир не проведёт операцию без него | То же, `requireReceiptNumber` |
| Потолок суммы для кассира | Кассир не проведёт операцию больше указанной | То же, `maxManualAmount` |
| Отслеживание подозрительных клиентов | Алерт, если гость делает слишком много покупок (порог до 50) | Расширяем: следим и за гостем, и за кассиром |
| История действий сотрудников | Кто что настроил и когда | То же, `AuditLog` |
| RFM-сегменты | Отдельная вкладка статистики | Считаем, но используем для авто-сегментов рассылок |
| Отчёт по сотрудникам | Кто сколько операций провёл | То же + доход сотрудника |
| Сертификаты, теги, источники трафика | Отдельные модули | Берём, но в v2 |

### Взяли у других

- **Talon.One и Voucherify** — движок правил с приоритетами и объяснимым результатом. У UDS акции плоские, у нас — цепочка с приоритетом и флагом стекирования.
- **Square и Toast** — автоматические кампании по триггеру, а не только ручные рассылки.
- **Smile.io** — earning rules как данные, а не как код: новую механику добавляем строкой в конфиг.
- **Starbucks** — визуальный прогресс и стрики.
- **Loyverse** — бесплатный тариф без лимита по числу гостей как главный крючок.
- **LINE MyCustomer** — rich menu как точка входа для тайской аудитории.

### Сознательно НЕ берём у UDS

**Трёхуровневую реферальную систему.** В их кабинете это 5% / 3% / 1% с покупок приглашённых на трёх уровнях вглубь. Это буквально многоуровневый маркетинг, и именно он даёт UDS репутационный шлейф MLM, задокументированный в ресерче. У нас реферал **одноуровневый**: награда пригласившему и приглашённому один раз, с лимитом и защитой от самореферала.

**Процент кассиру от суммы счёта.** В их кабинете это одно поле «Размер вознаграждения, %» — 0,90% от суммы каждой операции. Такая схема прямо оплачивает накрутку: чем больше операций провёл, тем больше получил, независимо от того, настоящий гость или свой номер. У нас по умолчанию — фиксированная сумма за нового гостя с дозреванием при втором визите. Процент оставляем как опцию, но с пятью правилами отклонения.
