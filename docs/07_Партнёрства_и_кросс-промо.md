# POSitive Loyalty — партнёрства и кросс-промо между заведениями

Версия 1.0 · для Claude Code

---

## 1. Что это и почему это ложится на существующую архитектуру

Два заведения внутри сети договариваются между собой — без участия платформы — и дают бонусы гостям друг друга. Студия танцев продала абонемент на 5 000 ฿ — гостю в приложение тут же прилетает промокод от ресторана «Тайнуки»: «Филадельфия в подарок при заказе от 800 ฿, действует до 31 августа».

**Ключевое архитектурное наблюдение.** Это не новая подсистема. Это уже спроектированный «ваучер сети» (Offer с `visibility: NETWORK`), у которого:

- триггер срабатывает **в другом заведении**, а не в своём;
- аудитория — **гости конкретного партнёра**, а не вся сеть;
- условия согласованы **двумя сторонами**, а не одной.

Награду оплачивает тот, кто её даёт — как и в ваучерах сети. Клиринга между юрлицами нет. Значит, регуляторный риск e-money не возникает, а модель данных расширяется тремя таблицами, а не переписывается.

**Что это даёт бизнесу.** Заведение получает канал привлечения, за который не платит ни нам, ни агрегатору — платит только собственным продуктом и только по факту прихода гостя. Для нас это сетевой эффект в чистом виде: чем больше заведений, тем ценнее каждому быть внутри.

## 2. Термины

| Термин | Что означает |
|---|---|
| **Партнёрство** (Partnership) | Связь двух тенантов. Контейнер для условий и переписки |
| **Условие** (Term) | Одностороннее обязательство: «заведение B даёт награду X гостям заведения A при событии Y». В партнёрстве может быть 0–N условий в каждую сторону |
| **Триггер** | Событие в заведении-источнике, по которому выдаётся награда |
| **Приглашение** (Invite) | Первое сообщение, открывающее партнёрство. Ограничено квотой |
| **Заведение-источник** (`triggerTenant`) | Где происходит событие — студия танцев |
| **Заведение-донор** (`rewardTenant`) | Кто даёт награду — ресторан |

Направление всегда явное. «Тайнуки даёт Филадельфию гостям студии при покупке абонемента» — это одно Term: `triggerTenant = студия`, `rewardTenant = Тайнуки`. Встречное условие «студия даёт скидку 10% гостям Тайнуки» — другое Term с обратными ролями. Партнёрство может быть и односторонним.

## 3. Модель данных

```prisma
model Partnership {
  id                String   @id @default(uuid())
  initiatorTenantId String
  partnerTenantId   String
  status            PartnershipStatus @default(PROPOSED)
  // PROPOSED → NEGOTIATING → ACTIVE → PAUSED → ENDED | DECLINED
  proposedAt        DateTime @default(now())
  acceptedAt        DateTime?
  endsAt            DateTime?                    // null = бессрочно
  endedBy           String?
  endReason         String?

  terms             PartnershipTerm[]
  messages          PartnershipMessage[]

  @@unique([initiatorTenantId, partnerTenantId])  // одна пара — одно партнёрство
  @@index([partnerTenantId, status])
  @@index([initiatorTenantId, status])
}

model PartnershipTerm {
  id               String   @id @default(uuid())
  partnershipId    String
  triggerTenantId  String                        // где происходит событие
  rewardTenantId   String                        // кто даёт награду
  offerId          String   @unique              // порождённый Offer у rewardTenant

  trigger          Json                          // см. 4.1
  reward           Json                          // см. 4.2
  validityDays     Int      @default(7)          // сколько живёт выданный промокод
  limits           Json                          // {totalGrants, perGuest, dailyCap}

  status           TermStatus @default(DRAFT)    // DRAFT | PROPOSED | ACCEPTED | ACTIVE | PAUSED | ENDED
  proposedBy       String                        // tenantId
  acceptedBy       String?
  acceptedAt       DateTime?

  grantsIssued     Int      @default(0)
  grantsRedeemed   Int      @default(0)

  partnership      Partnership @relation(fields: [partnershipId], references: [id])
  @@index([triggerTenantId, status])
}

model PartnershipMessage {
  id             String   @id @default(uuid())
  partnershipId  String
  fromTenantId   String
  kind           MessageKind                     // INVITE | TEXT | TERM_PROPOSED | TERM_ACCEPTED | TERM_REJECTED | SYSTEM
  text           String                          // оригинал
  sourceLang     String                          // язык оригинала
  translations   Json                            // {"th": "...", "en": "..."} — кэш перевода
  termId         String?
  createdAt      DateTime @default(now())
  readAt         DateTime?
  @@index([partnershipId, createdAt])
}

model InviteQuota {
  tenantId   String
  date       DateTime @db.Date
  freeUsed   Int      @default(0)
  paidUsed   Int      @default(0)
  @@id([tenantId, date])
}

model InviteBlock {
  blockerTenantId  String
  blockedTenantId  String
  reason           String?
  createdAt        DateTime @default(now())
  @@id([blockerTenantId, blockedTenantId])
}

model PartnershipPricing {                       // настраивает админ платформы
  id             String  @id @default(uuid())
  vertical       Vertical?                       // null = по умолчанию для всех
  freeInvitesPerDay  Int @default(3)
  extraInvitePrice   Int                         // в минорных единицах, 0 = бесплатно
  maxActivePartnerships Int @default(20)
  updatedAt      DateTime @updatedAt
}
```

Дополнения к существующим моделям:

```prisma
model Tenant {
  // …
  ownerLocale          String  @default("th")    // язык владельца для переводов
  openToPartnerships   Boolean @default(true)    // виден ли в каталоге партнёров
  partnershipPitch     String?                   // короткое «о нас» для каталога, i18n через translations
}

model Offer {
  // …
  partnershipTermId String? @unique              // если акция порождена партнёрством
  visibility  Visibility  // VENUE_ONLY | NETWORK | PARTNER  ← новое значение
}
```

**Важно:** Term при активации **порождает Offer** у `rewardTenant` с `visibility: PARTNER` и `audience: {kind: 'PARTNER_GUESTS', triggerTenantId}`. Дальше работает существующий конвейер: OfferGrant, погашение на кассе, статистика, антифрод. Партнёрство — надстройка над акциями, а не параллельная система.

## 4. Триггеры и награды

### 4.1 Триггеры

Что должно произойти у `triggerTenant`, чтобы гость получил награду от `rewardTenant`.

```ts
export const PartnershipTrigger = z.discriminatedUnion('type', [
  z.object({ type: z.literal('ON_PURCHASE'),
             minAmount: z.number().int().min(0) }),          // чек от N
  z.object({ type: z.literal('ON_FIRST_VISIT') }),           // первый визит гостя
  z.object({ type: z.literal('ON_NTH_VISIT'),
             n: z.number().int().min(2) }),                  // N-й визит
  z.object({ type: z.literal('ON_SALE_KIND'),
             saleKindId: z.uuid(),
             minAmount: z.number().int().min(0) }),          // купил абонемент/курс/аренду
  z.object({ type: z.literal('ON_STAMP_COMPLETE') }),        // закрыл штамп-карту
  z.object({ type: z.literal('ON_TIER_REACHED'),
             tierId: z.string() }),                          // достиг статуса
  z.object({ type: z.literal('ON_MEMBERSHIP') }),            // просто стал гостем партнёра
])
```

**ON_SALE_KIND — головной пример этого документа, и он потребовал справочника.**

Раньше здесь стоял `ON_PACKAGE_PURCHASE`, отличавшийся от `ON_PURCHASE`
происхождением записи в журнале. Сработать он не мог никогда: журнал знает
только чеки, и абонемент в нём ничем не помечался — механика была верной
и мёртвой.

Вид продажи (`SaleKind`, docs/02 раздел 5.7) ведёт само заведение-источник:
у студии это «абонемент на 10 занятий», у проката — «сутки» и «неделя».
Кассир выбирает из списка, когда проводит начисление. Донор видит название
по двусторонней политике партнёрства — иначе соглашался бы вслепую
на идентификатор.

**Кассе партнёра ничего не требуется.** Начисление проводит человек в нашем
приложении: у партнёра своя касса для денег, наша — для лояльности. Условие
работает у заведения, которое про POSitive POS никогда не слышало.

**Как триггеры доезжают до модуля.** Ранняя редакция этого документа обещала,
что они «вычисляются из доменных событий, которые уже эмитит ledger:
`ledger.earned`, `membership.created`, `stamp.completed`, `tier.changed`,
`package.purchased`». Такой шины в коде нет и не появилось: единственное,
что похоже на неё, — лента для экрана в зале, которая пропускает лишь
начисления по чекам, маскирует имя гостя и живёт в памяти процесса.

Вместо шины разгребатель сам находит в журнале операции, которых ещё не видел,
и зовёт слушателя — тем же способом, которым устроены исходящие события к кассе.
Журнал долговечен, поэтому «операция есть, а награда не выдана» — состояние,
из которого всегда можно доехать. Цена: награда приходит не мгновенно,
а в ближайший проход (до десяти секунд).

`stamp.completed` и `tier.changed` по-прежнему не существуют: штампов и статусов
в системе нет. Условия с такими триггерами согласовать можно, они просто
не сработают, пока механики нет.

### 4.2 Награды

Что получает гость у `rewardTenant`.

```ts
export const PartnershipReward = z.discriminatedUnion('kind', [
  z.object({ kind: z.literal('FREE_ITEM'),
             itemName: z.string(), minCheck: z.number().int().default(0) }),
  z.object({ kind: z.literal('FIXED_POINTS'), amount: z.number().int() }),
  z.object({ kind: z.literal('PERCENT_OFF'),
             percent: z.number().min(1).max(100), maxDiscount: z.number().int().nullable() }),
  z.object({ kind: z.literal('FIXED_OFF'),
             amount: z.number().int(), minCheck: z.number().int().default(0) }),
  z.object({ kind: z.literal('GIFT_STAMPS'), count: z.number().int().min(1) }),
])
```

Каждое условие содержит `validityDays` — через сколько дней сгорает выданный промокод. Это то, что владелец в примере называл «действует до определённого срока».

### 4.3 Как это выглядит в примере пользователя

> Студия танцев: «клиент купил абонемент на 5 000 ฿». Тайнуки: «Филадельфия в подарок при заказе от 800 ฿, действует 14 дней».

```json
{
  "triggerTenantId": "dance_studio",
  "rewardTenantId": "tainuki",
  "trigger": { "type": "ON_SALE_KIND", "saleKindId": "3f0c…", "minAmount": 500000 },
  "reward":  { "kind": "FREE_ITEM", "itemName": "Ролл Филадельфия", "minCheck": 80000 },
  "validityDays": 14,
  "limits": { "totalGrants": 200, "perGuest": 1, "dailyCap": 10 }
}
```

`dailyCap` защищает Тайнуки от того, что студия проведёт акцию и за один день пришлёт двести человек за бесплатными роллами.

## 5. Жизненный цикл партнёрства

```
[A ищет партнёра в каталоге] → [A отправляет приглашение]     квота списана
                                        ↓
                              PROPOSED · B получает уведомление на своём языке
                                        ↓
              B: «Отклонить» → DECLINED          B: «Обсудить» → NEGOTIATING
                                                          ↓
                                   переписка + предложения условий (Term: PROPOSED)
                                                          ↓
                                   каждая сторона принимает условия другой (Term: ACCEPTED)
                                                          ↓
                    хотя бы одно Term ACCEPTED с обеих сторон или одностороннее — партнёрство ACTIVE
                                                          ↓
                                   Term активируется → порождает Offer у rewardTenant
                                                          ↓
                    любая сторона: PAUSED (свои Term) · ENDED (всё партнёрство, с уведомлением)
```

**Правила, которых нельзя нарушать:**

1. Term активируется **только после принятия обеими сторонами**. Заведение-донор не может быть обязано давать награду без своего согласия — очевидно. Но и заведение-источник должно согласиться: оно отвечает за то, что его гостям придёт чужое предложение.
2. Любая сторона может **приостановить своё Term в один тап**, без объяснений. Уже выданные промокоды продолжают действовать до истечения — гостя нельзя обмануть.
3. Завершение партнёрства — с уведомлением второй стороне и **7-дневным периодом**: новые промокоды не выдаются, выданные догорают.
4. Изменение условия активного Term = новое Term на согласование. Старое продолжает работать до принятия нового. Никаких «тихих» правок.

## 6. Приглашения, квоты и цены

### 6.1 Квота

Каждое заведение может отправить N бесплатных приглашений в сутки. N задаёт админ платформы — по умолчанию 3, можно по вертикали. Сверх квоты — платно, цена тоже из админки. Счётчик сбрасывается в полночь по таймзоне заведения.

```
POST /v1/admin/partnerships/invites
→ 402 INVITE_QUOTA_EXCEEDED { "freeLeft": 0, "extraPrice": 5000, "currency": "THB" }
→ клиент показывает «Бесплатные приглашения на сегодня закончились. Ещё одно — 50 ฿» с кнопкой оплаты
```

Оплата — через биллинг тенанта (та же карта, что для подписки). Это отдельная строка выручки платформы — небольшая, но она же решает задачу антиспама честнее любых фильтров.

### 6.2 Антиспам без модератора

| Правило | Зачем |
|---|---|
| Одна пара тенантов — одно партнёрство. Повторное приглашение после DECLINED — не раньше чем через 30 дней | Нельзя долбить одно заведение |
| Получатель может заблокировать отправителя навсегда | Абсолютный стоп |
| Три отклонения от разных получателей за неделю → квота отправителя падает до 1 в день на 30 дней | Автоматическое охлаждение спамера |
| Приглашение без текста не отправляется; минимум 40 символов | Заставляет написать хоть что-то по существу |
| Шаблоны приглашений — предзаполнены и редактируемы | Снимают барьер написать первое сообщение |
| Максимум активных партнёрств на тенанта — из админки, по умолчанию 20 | Гость не должен утонуть в чужих ваучерах |

Никакой ручной модерации в MVP. Жалоба «спам» → блокировка + событие в risk-лог платформы. Если один тенант получает 5 жалоб — его квота обнуляется до разбора админом.

### 6.3 Каталог партнёров

Заведение видит других участников сети: категория, район, расстояние, число гостей (округлённо: «~500 гостей»), «открыт к партнёрствам», короткий питч, языки владельца. Точные цифры базы не показываем — это чужие коммерческие данные.

Фильтры: категория, район, «дополняющие» (ресторан видит сначала спа и прокат, а не другие рестораны — конкурентов договариваться труднее).

## 7. Переписка и автоперевод

Каждый тенант при регистрации указывает `ownerLocale` — язык владельца. Приглашение и все сообщения хранятся в оригинале и **переводятся на язык получателя** автоматически при отправке.

```ts
// apps/api/src/partnerships/translation.service.ts
async translateForRecipient(msg: PartnershipMessage, recipientLocale: string) {
  if (msg.sourceLang === recipientLocale) return msg.text
  if (msg.translations[recipientLocale]) return msg.translations[recipientLocale]
  const translated = await this.provider.translate(msg.text, msg.sourceLang, recipientLocale)
  await this.cache(msg.id, recipientLocale, translated)
  return translated
}
```

Провайдер — за интерфейсом `TranslationProvider`. Первая реализация — DeepL (лучшее качество для тайского среди доступных API) с фолбэком на Google Translate. `[гипотеза, проверить качество на реальных текстах владельцев]`

**В интерфейсе:** сообщение показано на языке читателя с пометкой «переведено автоматически» и кнопкой «показать оригинал». Условия Term **не переводятся текстом** — они структурные, и рендерятся на языке читателя из шаблонов. «Филадельфия» — единственное текстовое поле в награде (`itemName`), оно переводится вместе с сообщением.

Уведомление о новом приглашении уходит владельцу в его канал (Telegram / LINE / почта) на его языке.

## 8. Как срабатывает триггер — сквозной путь

```
1. Гость Анна покупает абонемент в студии за 5 000 ฿
   → касса студии → ledger.earn(...) → событие ledger.earned {tenantId: studio, guestId, basisAmount: 500000, refType: 'package'}

2. PartnershipTriggerListener получает событие
   → SELECT terms WHERE triggerTenantId = studio AND status = ACTIVE
   → для каждого: matches(trigger, event)?  ON_SALE_KIND: вид совпал, 500000 ≥ 500000 → да

3. Проверка лимитов Term: perGuest (Анна ещё не получала), dailyCap (сегодня выдано 3 из 10), totalGrants
   → все пройдены

4. Выдача: offerGrantService.issue({ offerId: term.offerId, guestId, expiresAt: now + 14d })
   → OfferGrant создан у Тайнуки, код TNK-PHIL-7K2Q
   → идемпотентность: ключ = hash(termId, guestId, sourceLedgerEntryId) — повтор события не выдаст второй код

5. Уведомление Анне в её канал на её языке:
   «🎁 Подарок от партнёра: Тайнуки дарит ролл Филадельфия при заказе от 800 ฿. Действует до 1 сентября»
   → в кошельке появляется ваучер с пометкой «от партнёра студии»

6. Анна приходит в Тайнуки → кассир сканирует код → стандартное погашение (раздел 3.4 API)
   → term.grantsRedeemed++ → обе стороны видят в статистике
```

Событие обрабатывается асинхронно в очереди `partnership-triggers`. Касса студии ничего не ждёт.

**Если у гостя нет membership у Тайнуки** — оно создаётся при выдаче с `source: PARTNERSHIP`, `referredByTenantId: studio`. Так Тайнуки видит в своей базе: «этот гость пришёл от студии танцев». Это и есть измеримость кросс-промо, которой нет ни у одной офлайн-договорённости.

## 9. API

### Каталог и приглашения

```http
GET  /v1/admin/partners/catalog?category=SPA&near=me&radius=3000&complementary=true
POST /v1/admin/partnerships/invites
     { "partnerTenantId": "…", "text": "Мы студия танцев рядом с вами…", "proposedTerms": [Term?] }
     → 201 { partnershipId, quota: { freeLeft: 2 } }
     → 402 INVITE_QUOTA_EXCEEDED
     → 409 PARTNERSHIP_EXISTS
     → 403 BLOCKED_BY_RECIPIENT
GET  /v1/admin/partnerships/quota            → { freeLeft, freeLimit, extraPrice }
```

### Партнёрства

```http
GET   /v1/admin/partnerships?status=ACTIVE
GET   /v1/admin/partnerships/{id}            → партнёрство + terms + последние сообщения (переведённые)
POST  /v1/admin/partnerships/{id}/decline    { reason? }
POST  /v1/admin/partnerships/{id}/block
POST  /v1/admin/partnerships/{id}/end        { reason? }     → 7-дневный догон
```

### Переписка

```http
GET   /v1/admin/partnerships/{id}/messages?cursor=…
POST  /v1/admin/partnerships/{id}/messages   { text }        → сохраняется + переводится + уведомление
```

### Условия

```http
POST  /v1/admin/partnerships/{id}/terms      { triggerTenantId, rewardTenantId, trigger, reward, validityDays, limits }
POST  /v1/admin/partnerships/{id}/terms/{termId}/accept
POST  /v1/admin/partnerships/{id}/terms/{termId}/reject   { reason? }
POST  /v1/admin/partnerships/{id}/terms/{termId}/pause
POST  /v1/admin/partnerships/{id}/terms/{termId}/resume
GET   /v1/admin/partnerships/{id}/stats      → по каждому term: выдано, погашено, новых гостей приведено, оценка выручки
```

Правило авторизации: предложить Term может любая из сторон, но **принять — только та сторона, которая ещё не принимала**, и `rewardTenant` обязан принять явно. Проверяется на API, не в интерфейсе.

### Платформа

```http
GET   /v1/platform/partnerships/pricing
PUT   /v1/platform/partnerships/pricing      { vertical?, freeInvitesPerDay, extraInvitePrice, maxActivePartnerships }
GET   /v1/platform/partnerships/abuse        → жалобы, охлаждённые тенанты
```

## 10. Экраны

### Бэк-офис: раздел «Партнёры» `/partners`

Добавляется девятым пунктом меню. Три вкладки.

**Каталог.** Карточки заведений сети: название, категория, район, расстояние, «~500 гостей», питч, языки. Кнопка «Предложить партнёрство» → модалка с шаблоном текста и опционально готовым условием. Внизу модалки — остаток бесплатных приглашений на сегодня и цена дополнительного.

**Мои партнёрства.** Список с статусами. Карточка: логотипы двух заведений, статус, число активных условий в каждую сторону, метрики «привели нам / привели им».

**Партнёрство** (страница). Слева — переписка в виде чата с пометками перевода. Справа — условия в две колонки: «Мы даём их гостям» и «Они дают нашим гостям». Каждое условие — карточка с триггером, наградой, сроком, лимитами, статусом и кнопками принять / отклонить / пауза. Кнопка «Предложить условие» открывает конструктор — тот же визуальный язык, что конструктор акций, с живым превью того, что увидит гость.

### Приложение владельца

Уведомление о приглашении → экран партнёрства с переводом → кнопки «Обсудить» / «Отклонить». Принять условие можно с телефона в два тапа. Это важно: владелец массажного салона не сидит за компьютером.

### Гостевое приложение

Ваучер от партнёра в кошельке выглядит как обычный, но с строкой «Подарок от партнёра студии танцев» и логотипами обоих заведений. В карточке заведения-донора — блок «Партнёры» со списком, откуда могут прилететь подарки. Пуш при выдаче — на языке гостя.

## 11. Безопасность и антифрод

Всё из документа 05 применяется. Специфичные для партнёрств риски:

| Риск | Мера |
|---|---|
| Сговор двух тенантов для накрутки награды сотрудникам | Партнёрские гранты не считаются «новым гостем» для мотивации персонала донора — `StaffReward` не начисляется за membership с `source: PARTNERSHIP` |
| Заведение-источник фабрикует события ради подарков от партнёра | `dailyCap` и `totalGrants` у донора; risk-модуль видит всплеск триггеров от одного источника |
| Утечка коммерческих данных через каталог | Размер базы округляется до сотен; выручка, средний чек и список гостей не показываются никогда |
| Спам через приглашения | Квота, оплата, блокировки, автоохлаждение — раздел 6 |
| Гость получает ваучер от заведения, которому не давал согласия PDPA | Согласие гостя при регистрации включает пункт о предложениях партнёров сети; в профиле гостя есть выключатель «предложения партнёров» |
| Донор отключил Term, а гости с кодами уже идут | Выданные коды догорают до срока — правило 2 раздела 5. Донор видит это заранее в подтверждении паузы |

Кросс-тенантный тест расширяется: тенант C не может читать партнёрство A↔B, даже зная его id.

## 12. Что не делаем в первой версии

- Многосторонние партнёрства (три и более заведений в одном соглашении). Квесты — отдельный документ.
- Денежные расчёты между партнёрами. Никогда — это e-money.
- Ручную модерацию текстов. Только реакция на жалобы.
- Партнёрства между тенантами разных стран. Появится с выходом за пределы Таиланда.
- Публичный рейтинг «надёжности партнёра». Соблазнительно, но на маленькой сети превращается в травлю.
