# Развёртывание в общий проект Supabase

Как поселить систему лояльности в проект Supabase, где уже живёт другой продукт — например сайт, — не смешав их данные.

---

## Что мы делаем и почему именно так

Лояльность въезжает в **отдельную схему** базы. Таблицы сайта остаются в `public`, наши — в своей схеме. Одна база, две непересекающиеся области.

Это не просто «положить рядом». Ниже — три места, где схема обязана быть задана явно, и все три одинаково обязательны.

### Три места, и почему пропуск любого молчалив

| Что | Откуда берёт схему | Что будет без этого |
|---|---|---|
| Миграции Prisma CLI | `?schema=` в строке подключения; `prisma.config.ts` подставляет его из `DATABASE_SCHEMA` | Таблицы создаются в схеме сайта |
| Запросы, которые Prisma строит сама | опция `schema` драйвер-адаптера | В каждый идентификатор **зашивается литерал `public`** — приложение читает и пишет в схему сайта |
| Сырой SQL (`$queryRaw`) | `search_path` соединения | Неквалифицированные имена ищутся в схеме сайта |

Второй пункт — самый коварный. Драйвер-адаптер **не** «резолвит по `search_path`», как можно ожидать: без явной опции он подставляет `public` константой. Из этого следует важное:

> Настройка `ALTER ROLE ... SET search_path` **не чинит** такую сборку. В SQL буквально написано `"public"."LedgerEntry"`.

Худший сценарий: старые таблицы остались в `public` (скопировали вместо переноса, откатились, перенесли частично) — приложение молча продолжает писать журнал баллов туда. Сборка зелёная, тесты зелёные, ошибок нет.

Поэтому схема задаётся **одной** переменной `DATABASE_SCHEMA`, а `prisma.config.ts` выводит из неё `?schema=`. Физически невозможно, чтобы CLI и приложение указывали на разные схемы.

## Шаг 1. Подготовка проекта (делаете вы)

В Supabase, в проекте сайта, откройте **SQL Editor** и проверьте, что у вас есть право заводить роли:

```sql
SELECT rolcreaterole FROM pg_roles WHERE rolname = current_user;
```

Должно вернуться `true`. Если `false` — дальше идти нельзя: **вся изоляция заведений держится на том, что приложение ходит в базу не владельцем.** Владелец таблицы игнорирует и `REVOKE`, и политики RLS.

Создайте схему и роль приложения:

```sql
CREATE SCHEMA IF NOT EXISTS loyalty;

-- Роль заводится без пароля; пароль вы зададите следующей командой
-- и сохраните в менеджере паролей. В репозиторий он не попадает.
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'positive_app') THEN
    CREATE ROLE positive_app NOLOGIN;
  END IF;
END
$$;

ALTER ROLE positive_app LOGIN PASSWORD 'ПРИДУМАЙТЕ_ДЛИННЫЙ_ПАРОЛЬ';
```

**Схема лояльности не должна торчать наружу через API Supabase.** Проверьте в Settings → API, что в списке Exposed schemas нет `loyalty`. У нас свой API; PostgREST к нашим таблицам доступа иметь не должен.

## Шаг 2. Строки подключения

Supabase даёт два адреса, и они нужны **оба, для разного**:

- **Direct connection** (порт `5432`) — для миграций. Пулер не умеет всего, что нужно DDL.
- **Transaction pooler** (порт `6543`) — для приложения.

В локальный `.env` впишите:

```
# Миграции и seed — прямое соединение, владельцем
DATABASE_URL=postgresql://postgres:ПАРОЛЬ@db.ВАШ_ПРОЕКТ.supabase.co:5432/postgres

# Схема — одна на всё
DATABASE_SCHEMA=loyalty
```

Пароли в чат не отправляйте: они нужны только в вашем `.env` и в переменных окружения хостинга.

## Шаг 3. Накат миграций

```bash
pnpm db:deploy
```

Именно `db:deploy`, а **не** `db:migrate` и **ни в коем случае** не `db:reset`. Последняя сносит схему целиком; на общей базе это соседский сайт. Команда защищена: на неместной базе она откажется работать.

Миграция `20260828100000_schema_agnostic_functions` в конце **сама проверяет**, что в схеме сайта не осталось наших функций, и роняет накат, если остались.

---

## Шаг 4. Проверить, что изоляция действительно работает

Это не формальность. Настроенная на вид изоляция и работающая изоляция — разные вещи, и разница видна только проверкой.

**Наши таблицы в своей схеме, а не у соседа:**

```sql
SELECT table_schema, count(*)
FROM information_schema.tables
WHERE table_name IN ('LedgerEntry', 'Membership', 'Tenant')
GROUP BY table_schema;
```

Ожидается одна строка: `loyalty | 3`. Если появилась строка с `public` — миграции ушли не туда, останавливайтесь.

**Наши функции не в схеме сайта:**

```sql
SELECT n.nspname, p.proname
FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE p.proname IN (
  'auth_tenant_for_device', 'pos_link_for_merchant',
  'webhook_deliveries_due', 'ledger_entries_awaiting_delivery'
);
```

Все — в `loyalty`. Ни одной в `public`.

**RLS действительно закрывает данные.** Подключитесь **под ролью `positive_app`** (не `postgres`) и выполните:

```sql
SELECT count(*) FROM loyalty."Membership";
```

Обязано вернуть `0` — заведение не объявлено, значит не видно ничего. Если вернулось не ноль, вы подключены владельцем и изоляции нет.

## Шаг 5. Приложение

В переменных окружения хостинга (Railway):

```
DATABASE_URL=postgresql://positive_app:ПАРОЛЬ@ХОСТ-ПУЛЕРА:6543/postgres?pgbouncer=true
DATABASE_SCHEMA=loyalty
```

Обратите внимание: приложение ходит под `positive_app`, а не под `postgres`. Это и есть граница.

## Что осталось непроверенным

Честный список того, что нельзя подтвердить, не подключившись к реальному проекту:

- **Поведение `search_path` через транзакционный пулер.** Параметр задаётся при подключении; в режиме транзакционного пулинга соединения переиспользуются, и поведение может отличаться от прямого соединения. Подстраховка уже есть: вызовы функций не полагаются только на `search_path`, а сама схема продублирована опцией адаптера. Но проверить сырой SQL дашборда на живом пулере — обязательный шаг.
- **Права `postgres` в конкретном проекте.** Возможность `CREATE ROLE` и `ALTER DEFAULT PRIVILEGES` зависит от тарифа и настроек.
- **Сама миграция `20260828100000`** написана, но не выполнена ни на одной базе: локальный PostgreSQL на момент написания был недоступен. Первый накат обязан идти на одноразовую копию, а не сразу на проект с сайтом.

---

## Порядок, если что-то пойдёт не так

Резервные копии в Supabase общие на проект. Восстановление откатит **и сайт тоже**. Поэтому:

1. Сначала накатите на пустой тестовый проект Supabase — убедитесь, что все проверки шага 4 проходят.
2. Только потом на проект с сайтом.
3. Перед накатом на общий проект сделайте резервную копию и убедитесь, что знаете, как её восстановить.
